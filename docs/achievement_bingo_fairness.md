# ADR: персонализация, сложность и fairness сезонного Bingo 4×4

- **Статус:** принято направление `bingo-v2`; числовые defaults требуют calibration,
  ещё не реализовано
- **Дата решения:** 18 августа 2026
- **Связанные задачи:** #212, #213, #215, #216
- **Текущая реализация:** `bingo-v1` остаётся preview-only и проверяет только горизонтальные ряды

Этот документ фиксирует продуктовые и технические решения для следующей версии
генератора. Он не утверждает, что production-сезон уже готов: `Season`, `Board`, `Cell`,
сезонные progress events, claims и player UI по-прежнему отсутствуют.

Уровни фиксации решений:

| Статус | Решение |
|---|---|
| Принято | считаются все 10 линий поля 4×4 |
| Принято | `play_deck` требует три турнира после активации |
| Принято | сложность персональна, а выигрышные линии должны быть сопоставимы по весу |
| Target default | логарифмический вес, dependency-aware replay и imbalance ≤10% |
| Требует calibration | bucket thresholds, prior strength `κ`, confidence gate и темп 7–9 турниров |

## 1. Зачем меняем модель

Квоты `4 easy / 6 medium / 4 hard / 2 rare` не гарантируют честное поле сами по себе.
Одна и та же клетка может быть простой для регулярного игрока и почти невозможной для
новичка; случайная раскладка способна собрать лёгкую выигрышную линию из формально разных
механик, которые закрываются одними и теми же турнирами.

Цель `bingo-v2`:

- поддерживать интерес в течение четырёхмесячного сезона, а не раздать большинство
  клеток за один вечер;
- давать разным игрокам разные, но сопоставимые по достижимости поля;
- не требовать высокого винрейта для каждого маршрута к бинго;
- объяснять и воспроизводить каждое решение генератора;
- не менять активированное поле при последующей перекалибровке модели.

## 2. Термины

- **Baseline snapshot** — замороженная история игрока и меты на момент генерации поля.
- **Candidate** — конкретная параметризованная цель: колода, соперник, threshold и другие
  параметры уже выбраны.
- **Opportunity** — событие, в котором клетка в принципе может получить прогресс:
  турнир, матч или peer-confirmation.
- **Прогрессивная клетка** — клетка со счётчиком `current / target`, которая может
  накапливать прогресс в нескольких событиях.
- **Completion probability** `p` — оценка вероятности закрыть клетку до конца сезона
  для конкретного игрока при замороженных параметрах.
- **Difficulty weight** `w` — числовая сложность клетки, полученная из `p`.
- **Winning line** — одна из десяти линий, закрытие которой считается Bingo.
- **Progress axis** — основной ресурс или тип события клетки: attendance, deck choice,
  result, opponent, club, social или peer confirmation.

## 3. Выигрышные линии

В поле 4×4 считаются ровно **10 линий**:

- `R0..R3` — четыре горизонтали;
- `C0..C3` — четыре вертикали;
- `D0` — главная диагональ `(0,0) → (3,3)`;
- `D1` — побочная диагональ `(0,3) → (3,0)`.

Квадраты 2×2, четыре угла и произвольные фигуры отдельным Bingo не считаются. Свободной
центральной клетки нет. Одна клетка входит в строку и столбец; диагональная клетка входит
ещё и в диагональ. Поэтому положение клетки является частью fairness, а не косметикой.

Генератор и диагностика должны использовать единый pure helper, возвращающий наборы
индексов всех выигрышных линий. UI, claims и тесты не должны независимо воспроизводить
геометрию поля.

## 4. Накопительный прогресс

В `bingo-v2` большинство целей должны требовать участия в нескольких событиях:

- на поле рекомендуется 9–11 прогрессивных клеток из 16;
- в каждой выигрышной линии — минимум две прогрессивные клетки;
- одноразовые «истории турнира» сохраняются ради эмоций, но не могут образовать
  случайно лёгкую линию;
- resettable streak допускается, но не больше одного на линию.

Один турнир может продвинуть несколько клеток. Искусственно выбирать только одну клетку
для зачёта нельзя: это непонятно игроку и усложняет audit. Корреляция такого прогресса
учитывается при оценке всей линии (§7).

### 4.1. «Сыграй на колоде X три турнира»

`play_deck` меняется с бинарного условия на счётчик с замороженными параметрами:

```json
{
  "deckGeneralName": "Blue Terror",
  "targetTournaments": 3,
  "statsSnapshotId": "..."
}
```

Зачёт одного шага требует одновременно:

- турнир начался не раньше активации поля;
- игрок сам записал колоду;
- игрок действительно появился в парингах;
- турнир закрыт и имеет полные результаты;
- `Archetype.general_name` совпадает с замороженной целью;
- этот `tournament_id` ещё не был засчитан в клетку.

Прогресс равен числу уникальных подходящих `tournament_id`, но не больше target. Completion
создаётся на третьем таком турнире и хранит все три источника evidence. Исправление или
повторный импорт того же турнира не добавляет второй шаг.

История до активации используется только для персонализации и оценки сложности. Она не
закрывает клетку и не создаёт стартовый прогресс.

Бот не знает, какими бумажными колодами владеет игрок. Способ назначения `deckGeneralName`
остаётся отдельным продуктовым решением: выбор из нескольких сопоставимых целей, один
предсезонный reroll или автоматическое назначение. До этого решения случайная недоступная
колода не может считаться `ready_for_season`.

## 5. Персонализация

Персонализируется не факт зачёта, а параметры кандидата и оценка его достижимости. После
активации они заморожены.

Baseline может учитывать:

- частоту реального участия и число оставшихся турниров доступных клубов;
- число знакомых `general_name` и частоту игры ими;
- winrate с размером выборки, а не только точечное значение;
- историю клубов;
- H2H и matchup только при достаточном числе матчей;
- недавнюю активность возможного target opponent;
- время, оставшееся до конца сезона.

Персонализация не должна превращаться в наказание активных игроков. По возможности
сохраняем одинаковый видимый target, например три турнира на колоде X, и меняем саму цель
или соседние клетки. Разные thresholds допустимы, только если они версионированы,
объяснимы и приводят к сопоставимой completion probability.

Если персонального baseline недостаточно:

- generic-механика может использовать сглаженный cohort prior;
- target-specific H2H/matchup-клетка отклоняется с reason code и заменяется fallback;
- отсутствие данных никогда не превращается в `p=1`, нулевой прогресс или автоматический
  completion.

## 6. Формула веса клетки

### 6.1. Оценка вероятности прогресса

Для механики с повторяющимися opportunities сначала оценивается вероятность `q`, что одна
будущая opportunity даст один шаг прогресса. Персональную оценку сглаживаем cohort prior,
чтобы короткая история не делала поле экстремальным:

```text
q̂ = (successes_player + κ × q_cohort) / (opportunities_player + κ)
```

`κ` — сила prior. Её значение выбирается по offline calibration и входит в
`estimatorVersion`; менять её внутри активного сезона нельзя.

Если до конца сезона есть `N` примерно одинаковых opportunities, а target равен `k`,
первое приближение completion probability:

```text
             k-1
p = 1 − Σ C(N,j) × q̂ʲ × (1−q̂)^(N−j)
             j=0
```

Это вероятность получить не меньше `k` успехов в `N` попытках. Для одной одноразовой цели
`k=1`. Для streak, неодинаковых tournament opportunities, H2H и peer-confirmation
используется versioned dynamic programming или Monte Carlo estimator, а не подмена
неподходящей binomial-формулой.

`N` учитывает не только календарь, но и сглаженную вероятность участия игрока. Для late
join расчёт производится на оставшемся интервале сезона. Если future schedule неизвестен,
используется явно версионированный forecast и это отражается в confidence.

### 6.2. Из вероятности в аддитивный вес

Вероятность ограничивается снизу и сверху, чтобы избежать бесконечного или нулевого веса:

```text
p_safe = clamp(p, 0.05, 0.95)
w = −log₂(p_safe)
```

Clamp нужен для численной устойчивости, а не для легализации невозможной клетки. Candidate
за пределами утверждённого probability/confidence band отклоняется или получает fallback;
точные границы входят в season calibration config.

Вес измеряется в битах сложности. Примеры:

| `p` | `w` |
|---:|---:|
| 0.95 | 0.074 |
| 0.80 | 0.322 |
| 0.50 | 1.000 |
| 0.25 | 2.000 |
| 0.10 | 3.322 |
| 0.05 | 4.322 |

Логарифм выбран потому, что для независимых клеток веса складываются:

```text
P(закрыть линию) ≈ p₁ × p₂ × p₃ × p₄ = 2^−(w₁+w₂+w₃+w₄)
```

`easy / medium / hard / rare` остаются понятными человеку bucket-метками. В контрактах
нужно различать:

- `baseDifficulty` — редакционная оценка механики в manifest;
- `effectiveDifficulty` — bucket конкретного кандидата для конкретного игрока;
- `completionProbability` и `difficultyWeight` — числовые замороженные значения.

Границы bucket определяются calibration config, а не разбросаны константами по коду.
`rare` дополнительно означает высокую дисперсию, редкую opportunity или внешнюю
зависимость; одна низкая `p` без проверки реальной доступности не делает клетку допустимой.

### 6.3. Confidence и версия модели

Рядом с `p` сохраняются:

- `estimatorVersion`;
- `baselineSnapshotId`;
- sample size и тип использованного prior;
- `confidence` или reason code низкой уверенности;
- прогнозное число opportunities;
- время расчёта и границы сезона.

Confidence не входит в вес как скрытый бонус. Низкая уверенность либо требует fallback,
либо явно учитывается в Board Lab и launch gate.

## 7. Вес выигрышной линии и зависимости

Быстрая оценка линии:

```text
W_sum(line) = Σ difficultyWeight(cell)
```

Она пригодна для pruning в solver, но не является финальной, потому что клетки зависимы.
Например, три турнира на колоде X одновременно могут закрыть участие, самостоятельную
регистрацию и прохождение всех раундов. Простая сумма посчитает один и тот же труд трижды.

Финальная оценка строится совместным historical replay или simulation, где одно
синтетическое/историческое событие двигает все подходящие клетки:

```text
p_line = P(все четыре клетки завершены до конца сезона)
W_joint(line) = −log₂(p_line_smoothed)
```

`p_line_smoothed` вычисляется с versioned Beta prior по числу совместных replay runs:

```text
p_line_smoothed = (completed_runs + α) / (total_runs + α + β)
```

`α`, `β` и минимальное число runs входят в `estimatorVersion`. Для линии нельзя
использовать cell-level floor `0.05`: произведение четырёх
допустимых вероятностей закономерно может быть меньше 5%, и жёсткий clamp скрыл бы разницу
между трудными линиями. Нулевой replay count превращается в низкую ненулевую posterior
probability с низким confidence, а не в бесконечность или автоматическую невозможность.

Для production fairness используется `W_joint`. `W_sum` разрешён только как preview
fallback до появления dependency-aware estimator и должен быть помечен в diagnostics.

Каждый candidate объявляет:

- `progressAxis`;
- `dependencyKeys`, например `tournament`, `deck:Blue Terror`, `opponent:123`;
- `varianceClass`;
- line-level incompatibilities для вложенных или конфликтующих условий.

Это позволяет solver отсечь очевидно коррелированные линии ещё до дорогого replay.

## 8. Критерий баланса десяти линий

Для каждого поля вычисляются веса всех десяти линий. Основная метрика:

```text
medianW = median(W_joint(line))
relativeImbalance = (max(W_joint) − min(W_joint)) / medianW
```

Принятый target для валидного production-поля:

```text
relativeImbalance ≤ 0.10
```

Равенство само по себе недостаточно: десять одинаково невозможных линий формально имеют
идеальный imbalance. Поэтому season config дополнительно задаёт допустимый диапазон
`p_line_min ≤ p_line ≤ p_line_max`. Его значения утверждаются после baseline replay и
замораживаются до activation.

Дополнительно показывается отношение вероятностей самой лёгкой и самой тяжёлой линии:

```text
probabilityRatio = 2^(max(W_joint) − min(W_joint))
```

Если bounded solver не находит поле в допуске, генерация завершается с diagnostics. Нельзя
молча расширять tolerance, менять thresholds или бесконечно перебирать seed.

Пример двух приблизительно равных независимых линий:

| Линия | Вероятности клеток | Суммарный вес | Вероятность линии |
|---|---|---:|---:|
| A | 0.90 × 0.85 × 0.80 × 0.70 | 1.223 | 42.8% |
| B | 0.95 × 0.90 × 0.75 × 0.65 | 1.262 | 41.7% |

## 9. Hard constraints каждой линии

Каждая из десяти линий обязана удовлетворять одинаковым ограничениям:

- минимум две прогрессивные клетки;
- минимум один маршрут без требования высокого baseline winrate;
- максимум одна `rare`;
- максимум одна peer-confirmed клетка;
- максимум одна клетка с тем же конкретным opponent;
- не больше двух клеток одного `progressAxis`;
- нет пары вложенных условий, которые почти гарантированно закрываются одним и тем же
  минимальным набором событий;
- нет пары явно конфликтующих целей без учёта дополнительной стоимости конфликта.

Ограничения уровня поля сохраняются:

- 16 уникальных candidates;
- одна mechanic не маскируется несколькими формулировками;
- максимум две peer-confirmed клетки;
- один конкретный opponent — максимум одна клетка на поле;
- data-blocked/ineligible candidate не попадает в поле;
- category quotas и разнообразие применяются вместе с числовой сложностью.

Диагонали проверяются теми же правилами. Отдельных облегчённых условий для них нет.

## 10. Solver `bingo-v2`

Генерация остаётся deterministic для фиксированного:

```text
seasonId + playerId + seed + algorithmVersion + catalogVersion
+ baselineSnapshotId + estimatorVersion + constraintsVersion
```

Рекомендуемый порядок поиска:

1. Параметризовать candidates по frozen baseline.
2. Отклонить недоступные и недостаточно подтверждённые цели.
3. Рассчитать `p`, `w`, confidence и dependency metadata.
4. Выбрать 16 candidates с board-level quotas.
5. Разложить их по позициям, проверяя частичные ограничения всех затронутых линий.
6. Минимизировать `relativeImbalance`, затем dependency/variance penalties.
7. Выполнить joint replay для финальных десяти линий.
8. Вернуть `BoardDraft` либо bounded `BoardGenerationError` с причинами.

Порядок candidates на входе не должен влиять на результат. Tie-break остаётся SHA-256
ranking, а не случайностью процесса или БД.

`bingo-v1` не изменяется задним числом. Новая геометрия, контракты и формула требуют нового
`ALGORITHM_VERSION`; старые preview должны оставаться byte-for-byte воспроизводимыми.

## 11. Изменения контрактов

Целевая форма `InstantiatedCandidate` дополняется полями:

```text
progressKind
targetValue
progressAxis
dependencyKeys
varianceClass
baseDifficulty
effectiveDifficulty
completionProbability
difficultyWeight
attainabilityConfidence
estimatorVersion
baselineSnapshotId
expectedOpportunities
```

Текущее поле `attainability` нельзя оставлять неоднозначным: в `bingo-v2` оно либо
переименовывается в `completionProbability`, либо получает ровно эту документированную
семантику.

`RowDiagnostic` заменяется/обобщается до `LineDiagnostic`:

```text
lineId
lineKind
cellIndexes
sumWeight
jointProbability
jointWeight
progressiveCount
rareCount
peerConfirmedCount
progressAxes
valid
violations
```

`BoardDiagnostics` хранит все десять линий, `relativeImbalance`, `probabilityRatio`, версии
estimator/constraints и признак использования fallback-оценки.

При persistence эти параметры копируются в frozen `BoardCell`. Пересчёт модели не меняет
активную клетку; корректировка невозможной цели оформляется отдельным auditable replacement
event с owner review.

## 12. Fairness-проверка до запуска

### 12.1. Property и seed tests

Для каждой fixture-persona минимум на 1000 seeds проверяем:

- перечислены ровно 10 уникальных выигрышных линий;
- каждая клетка входит в ожидаемые строки/столбцы/диагонали;
- все line и board constraints выполнены;
- `relativeImbalance ≤ 0.10`;
- joint probability каждой линии лежит в season-configured диапазоне;
- одинаковый frozen input даёт одинаковый JSON;
- невозможный pool даёт diagnostics, а не reroll;
- ни один no-data candidate не становится автоматически лёгким.

### 12.2. Historical replay

Для реального игрока baseline строится на момент `t0`, поле генерируется без просмотра
будущего, затем на него проигрываются реальные события `(t0, t0 + season_length]`.
Rolling точки `t0` дают выборку виртуальных сезонов без leakage.

Сравниваем по cohort и persona:

- вероятность получить хотя бы одно Bingo;
- число фактически сыгранных турниров до первой клетки и первой линии;
- долю полей без прогресса 30 дней;
- completion rate клеток и линий;
- разницу самой лёгкой и тяжёлой линии;
- долю прогресса, созданную одним турниром;
- зависимость результата от winrate, клуба, частоты участия и seed;
- вероятность полного поля.

Нельзя запускать сезон только потому, что 1000 синтетических boards формально прошли
constraints. Нужны replay, ручная выборка Board Lab и согласованные targets из #216.

## 13. Темп и длительное участие

Архитектура поддерживает следующий рекомендуемый ориентир, но точные targets требуют
baseline и отдельного утверждения:

- видимый прогресс после первого подходящего турнира;
- первая линия у регулярно участвующего игрока примерно после 7–9 посещённых турниров;
- несколько линий — ближе ко второй половине сезона;
- полное поле — редкий результат для самых вовлечённых игроков.

Оптимизировать только календарные дни нельзя: у клубов разное расписание, а у игроков —
разная доступность. Основная единица сравнения — число eligible tournaments/opportunities;
календарное время остаётся дополнительной продуктовой метрикой.

## 14. Открытые продуктовые решения

До `ready_for_season` нужно отдельно утвердить:

1. Как игрок получает deck-X target: выбор из трёх, один reroll или автоматическое назначение.
2. Как масштабировать targets при late join и где находится cutoff активации.
3. Целевую вероятность первого Bingo и полного поля по cohort.
4. Может ли один игрок получить приз за линию и суперприз за полное поле.
5. Правило tie и owner review для клеток, закрытых одним турниром.
6. Calibration thresholds для difficulty buckets и значение prior strength `κ`.
7. Минимальный confidence, при котором generic candidate допустим без fallback.

Все значения должны войти в versioned season rules/config до activation. Изменять их для
уже активированных полей нельзя.

## 15. Consequences

Плюсы решения:

- все реальные пути к Bingo сравнимы, включая столбцы и диагонали;
- поле зависит от игрока без скрытого зачёта старой истории;
- накопительные цели поддерживают регулярное участие;
- вес имеет вероятностную интерпретацию и пригоден для audit;
- зависимости между клетками не маскируются красивой суммой статических tiers.

Цена решения:

- generator становится двухэтапным и требует estimator/replay;
- нужен больший baseline и versioned calibration;
- Board Lab должен показывать существенно более подробную диагностику;
- `bingo-v1` нельзя просто «подправить» — нужен отдельный контракт `bingo-v2`;
- без решения о доступности бумажных колод deck-X нельзя безопасно активировать публично.
