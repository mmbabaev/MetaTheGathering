# Форматы турнирных страниц AetherHub

AetherHub отдаёт страницу турнира (`/Tourney/RoundTourney/{id}?p={round}`) в **двух разных формах**. Это важно для парсинга парингов и счёта (`services/aetherhub_service.py`).

## Гипотеза: формат зависит от состояния турнира

> Пока турнир **активен** (идёт) — он в **js-формате**; после **завершения** становится **edinorog-форматом**.

Косвенные подтверждения (на момент написания):
- `99992` (🦄 Edinorog Pauper 08.06.2026, шёл в тот же день) — **js-формат**.
- `98984`, `99291` (завершённые) — **edinorog-формат**.

Не проверено «в лоб» на одном и том же турнире до/после — отсюда статус «гипотеза». Если подтвердится, то у активного турнира счёта нет, а после завершения у того же турнира счёт появится (и его можно добрать реимпортом — `import_tournament` для закрытого турнира обновляет только паринги/счёт).

## Сравнение

| | **edinorog** (завершённые) | **js** (активные) |
|---|---|---|
| Главная `?p=N`: таблица `matchList` | ✅ есть в серверном HTML | ❌ нет (паринги грузятся JS-ом, в HTML только standings) |
| Колонка «Match Results» (счёт `2 - 1`) | ✅ есть | ❌ нет |
| Откуда берём паринги | главная `?p=N` (matchList) | `RoundTourneyPublicPairings?id=&p=` (fallback) |
| Номер стола (колонка «Table») | ✅ | ✅ |
| Счёт матчей (`player_wins`/`opponent_wins`) | ✅ | ❌ (колонка результата пустая во всех раундах) |

## Как различает парсер

`AetherhubService._parse_pairings_page` ищет **только** `table#matchList`:
- главная `?p=N` содержит `matchList` → edinorog → паринги + столы + **счёт**;
- `matchList` нет (js-формат, главная = standings) → возвращаем пусто → `fetch_tournament` уходит в **fallback** на `RoundTourneyPublicPairings` → паринги + столы, **без счёта**.

⚠️ Нельзя брать «первую таблицу» (`tables[0]`) как паринги: на js-формате `tables[0]` — это standings (`Rank | Name | Points | Results | …`), и колонка **Points** попадает в имя оппонента → фейковый игрок «3»/«0» → краш импорта (см. регрессию, исправленную в PR с фиксом).

## Где используется счёт в проекте

`player_wins`/`opponent_wins` читаются **ровно в одном месте** — экспорт парингов в «формате Серёжи» (`ExportService.get_pairings_rows` → колонки `result1`/`result2`, `services/export.py`). Больше нигде (рейтинги/винрейты/уведомления его не используют). Поэтому у js-формат турниров пустой счёт влияет только на пустые `result1`/`result2` в их файле.

## Примеры ответов

В `docs/aetherhub_formats/` (обрезанные до релевантных таблиц):
- `edinorog_98984_main_p1_matchlist.html` — главная edinorog, таблица `matchList` со счётом в колонке «Match Results».
- `js_99992_main_p2_standings.html` — главная js-формата: **только** standings (`Rank/Name/Points/Results/…`), `matchList` нет. Именно `Points` ломал старый `tables[0]`-фолбэк.
- `js_99992_publicpairings_p2.html` — `RoundTourneyPublicPairings` js-формата: паринги есть, 4-я колонка (счёт) пустая.
