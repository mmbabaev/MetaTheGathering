# Система ачивок — план и текущее состояние

**Статус: lifetime hardening #199 — 7/7** (движок, теневой UI, eligibility,
immutable progress audit и безопасная player delivery). Публичный UI и продуктовые
подсказки остаются отдельными фазами. Разделы ниже описывают и то, что уже работает, и то, что впереди;
где это неочевидно, состояние помечено.

Контекст и каталог идей (зачем это вообще): [`ideas_engagement.md`](ideas_engagement.md) и
[`ideas_engagement_v2.md`](ideas_engagement_v2.md).

---

## 0. Принципы

1. **Ачивка = топливо маховика данных.** Игрок сам записался → бот знает его результаты → бот даёт
   ему ачивки и статистику → игрок возвращается и записывается снова. Поэтому в первой пятёрке
   обязательно есть ачивки, награждающие именно *саморегистрацию* и *запись чужих колод*.
2. **Прогресс засчитывается только за самостоятельную регистрацию.** Записал колоду сам — турнир
   идёт в зачёт; записал админ или оппонент — нет. Это единое правило для всех ачивок (§2.5).
3. **Стартуем в теневом режиме.** Движок считает ачивки и прогресс на каждом завершённом турнире,
   но игроки не видят ни UI, ни уведомлений — весь результат приходит **одним агрегированным
   сообщением владельцу** (§6). Переключение на игроков — потом, одной точкой в коде.
4. **Не выдаём то, что не можем честно посчитать.** Все ачивки первой фазы считаются только по
   данным собственной БД (`RoundPairing` + `Participant` + `Tournament`). Без DataLens, без
   архетипа оппонента.
5. **Идемпотентность важнее красоты.** Импорт AetherHub повторяется много раз за вечер, джобы
   перезапускаются. Выдача ачивки и апдейт прогресса должны быть безопасны при любом числе
   повторных вызовов.
6. **Одна фаза = один PR = работающий инкремент.**

## 2. Ограничения данных

### 2.1. Что можно честно посчитать уже сейчас

- собственный результат в турнире (W-L-D, место, X-0);
- счёт конкретного матча (2-0 / 2-1);
- собственную колоду и её историю по турнирам;
- участие/посещаемость по клубам и датам;
- кто записал колоду (свою/чужую).

### 2.2. Чего нельзя (и поэтому нет в первых фазах)

- **архетип оппонента** — известен, только если оппонент зарегистрирован и колода записана;
- **порядок игр внутри матча** — «камбек после 0-1» не отличить от 2-1 в другом порядке;
- **личность оппонента как игрока бота** — импортные плейсхолдеры (`tg_id < 0`) это люди без
  аккаунта;
- **сезоны и рейтинг силы** — их нет, нужен отдельный слой (§11).

### 2.5. Гейт «сам записался» — единое правило зачёта

Турнир идёт в зачёт ачивок игрока, только если он **сам записал свою колоду**:

```python
def counts_for_achievements(participant: models.Participant, user: models.User) -> bool:
    return (
        participant.archetype_id is not None
        and not participant.added_by_admin
        and participant.deck_added_by_tg_id == user.tg_id
    )
```

Это один из четырёх независимых gates: каждое rule также явно объявляет
`actually_played`, `tournament_closed` и `result_complete`. Применяется **ко всем**
спортивным/колодным ачивкам и ко всему прогрессу: серия «Завсегдатая» считается только по
турнирам с самозаписью, «Без поражений» не выдаётся, если колоду вписал админ, «Мультикласс»
считает только самостоятельно записанные деки. Единственное исключение — «Метаписец», который по
определению награждает собственное действие игрока (запись чужих колод).

Так ачивки становятся прямым стимулом к цели №2 — саморегистрации: чужая доброта не двигает твой
прогресс.

**Следствие, которое надо принять сознательно:** игрок, за которого колоду вписал админ, увидит
себя в стендингах с 4-0, но ачивку не получит. В сообщении о прогрессе это нужно проговаривать
(«турнир не в зачёт — колоду записал не ты»), иначе выглядит как баг.

## 3. Ачивки первой фазы (8 штук, 20 уровней) ✅ реализовано

Все считаются **только по собственной БД**. Общие правила выдачи:

- получатель — только реальный аккаунт (`User.tg_id > 0`); плейсхолдеры импорта пропускаем;
- турнир учитывается, только если завершён и полон (`is_tournament_complete()`) — иначе
  промежуточный импорт выдал бы «X-0» после первого раунда;
- участие игрока в турнире засчитывается по правилу §2.5;
- ачивка выдаётся один раз (`user_id + code + level`), повторная оценка ничего не меняет.

### 3.1. 🎖 Дебют (`debut`)

**Правило:** игрок впервые сам записал свою колоду на турнир.

- Источник: `Participant` (`archetype_id IS NOT NULL`, `deck_added_by_tg_id == user.tg_id`),
  первый по `Tournament.started_at`/`created_at`.
- Прогресса нет — одноразовая.
- Причина в отчёте: «первая своя колода: Mono Red Madness, Pauper 24.07.2026».

### 3.2. 🏆 Без поражений (`undefeated`, уровни I/II/III)

**Правило:** турнир пройден без поражений и ничьих (X-0), сыграны все раунды.

- Источник: `get_undefeated_players(tournament_id)` — готовый список, уже используется в отбивке
  «сбор метагейма завершён».
- Уровни: **I** — 1 раз, **II** — 3 раза, **III** — 10 раз. Прогресс = число X-0 турниров.
- Краевое: **бай считается победой** — так уже работает `_player_records()`; расходиться с отбивкой
  в чате нельзя, иначе игрок увидит себя в списке X-0 без ачивки.
- Причина: «4-0 на Elves; всего X-0 турниров: 3 (17.07 Burn, 10.07 Elves)».

### 3.3. 🧙 Метаписец (`scribe`, уровни I–IV)

**Правило:** записал N **чужих** колод суммарно за всё время. Уровни: 3 / 10 / 25 / 50.

- Источник: `Participant.deck_added_by_tg_id == user.tg_id AND Participant.user_id != user.id`.
- Аудитория правила шире остальных: в неё попадают все, кто записывал колоды на этом турнире,
  даже если сам в нём не играл.
- Прогресс = число записанных чужих колод.
- Причина: «записал сегодня: Иванов, Петров, Сидоров».

### 3.4. 📅 Завсегдатай (`regular`, уровни I/II/III)

**Правило:** участие (с самозаписью, §2.5) в N подряд идущих турнирах своего клуба. Уровни: 4 / 8 / 16.

- Источник: `Participant` × `Tournament(club, started_at)`. Все завершённые турниры клуба по
  возрастанию даты → цепочка присутствия → текущая серия.
- Серии считаем **отдельно по каждому клубу**; турниры без `club` и без парингов исключаем из
  цепочки (пустой турнир не разрывает серию).
- Прогресс = длина текущей серии.
- Причина: «4 турнира подряд в Goldfish: 03.07, 10.07, 17.07, 24.07».

### 3.5. 🎭 Мультикласс (`multiclass`, уровни I/II/III)

**Правило:** сыграл на N разных архетипах за последние 90 дней. Уровни: 3 / 5 / 8.

- Источник: `Participant.archetype` по турнирам с самозаписью за окно 90 дней; разные деки
  считаем по `Archetype.general_name` (чтобы «Blue Delver» и «Blue Terror» не сошли за две), при
  отсутствии — по `Archetype.name`.
- Прогресс = число разных дек в окне. Окно скользящее: прогресс может уменьшаться, **но уже
  выданная ачивка не отзывается** — выдал навсегда.
- Причина: «2/3 деки за 90 дней: Mono Red Madness (17.07), Elves (24.07)».
- Зачем: двигает разнообразие меты и даёт повод пробовать новое, а не приходить на одной деке.

> Заметка: раньше в этой позиции стоял «Еретик» (3-1 на деке вне топ-меты). Недельный
> `Archetype.meta_rank` теперь обновляется автоматически по годовому окну, но для lifetime-правила
> всё ещё нужно зафиксировать, какой именно snapshot считать на дату турнира. «Мультикласс» не
> зависит от меняющегося рейтинга; «Еретик» остаётся кандидатом на будущее (§11).

### 3.6. ⚡ Буду первый (`first_deck`, уровни I/II/III)

**Правило:** записал свою колоду на турнир раньше всех остальных. Уровни: 1 / 3 / 10 раз.

- Источник: минимальный `Participant.created_at` среди прошедших гейт §2.5 участников турнира
  (регистрация в боте идёт сразу с выбором колоды). При совпадении времени — меньший id.
- Прогресс = сколько раз игрок был первым.
- Причина: «первым записал колоду сегодня: 03.07 · 17.07 · 24.07».
- Зачем: гонка за ранней записью — ровно то поведение, которого мы хотим от игроков.

### 3.7. 💍 Однолюб (`loyalist`, уровни I/II/III)

**Правило:** N турниров подряд на одной и той же колоде. Уровни: 3 / 5 / 10.

- Источник: цепочка **собственных участий** игрока (не всех турниров клуба): пропуск турнира
  верность колоде не рвёт, смена архетипа — рвёт. Дека сравнивается по `general_name`.
- Прогресс = длина текущей серии.
- Причина: «Burn: 10.07 · 17.07 · 24.07».
- Ограничение: деклистов у бота нет, поэтому «без изменений в мейне» проверить нельзя — трактуем
  как «тот же архетип».

## 4. Модель данных

Две новые таблицы. Определения ачивок живут **в коде** (как `KNOWN_FLAGS` в feature flags) — их не
редактируют из UI, они версионируются вместе с логикой.

### 4.1. Выданные ачивки

```python
class UserAchievement(Base):
    """Выданная игроку ачивка. Одна строка = (игрок, код, уровень) навсегда."""

    __tablename__ = "user_achievements"

    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)
    code = Column(String(32), nullable=False)          # "undefeated"
    level = Column(Integer, nullable=False, default=1) # 1/2/3 для многоуровневых
    tournament_id = Column(Integer, ForeignKey("tournaments.id", ondelete="SET NULL"), nullable=True)
    progress_value = Column(Integer, nullable=True)    # значение счётчика на момент выдачи
    evidence = Column(String(512), nullable=True)      # причина: «4-0 на Elves», «серия 03.07…24.07»
    awarded_at = Column(DateTime, default=utc_now, nullable=False)
    notified_at = Column(DateTime, nullable=True)      # NULL = ещё не сообщили (кому — см. §6)

    __table_args__ = (UniqueConstraint("user_id", "code", "level", name="uq_user_achievement"),)
```

### 4.2. Прогресс

Нужен, чтобы (а) показывать «2/3» до выдачи, (б) считать **дельту** — что изменилось именно на
этом турнире, а не абсолютное значение.

```python
class UserAchievementProgress(Base):
    """Текущее значение счётчика ачивки у игрока. Одна строка = (игрок, код)."""

    __tablename__ = "user_achievement_progress"

    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)
    code = Column(String(32), nullable=False)
    value = Column(Integer, nullable=False, default=0)          # 2 деки, 7 колод, серия 3
    tournament_id = Column(Integer, ForeignKey("tournaments.id", ondelete="SET NULL"), nullable=True)  # когда обновили
    evidence = Column(String(512), nullable=True)               # из чего сложилось (для сообщения)
    updated_at = Column(DateTime, default=utc_now, onupdate=utc_now, nullable=False)

    __table_args__ = (UniqueConstraint("user_id", "code", name="uq_user_achievement_progress"),)
```

Прогресс — **производная величина**: он всегда пересчитывается правилом из первичных данных, а
таблица хранит последний посчитанный снапшот. Значит, её можно в любой момент снести и пересобрать
бэкафиллом; рассинхрон невозможен по построению.

**Миграция:** `alembic/versions/2c906a8d5c01_add_achievements.py` — обе таблицы разом,
`down_revision = 7c178567f22c`.

### 4.3. Immutable progress audit

Каждое реальное изменение snapshot создаёт `AchievementProgressEvent`: before/after,
evidence, source tournament/match ids, requirements, processing run, ruleset/stats version
и уникальный idempotency key. CLI `achievements events` показывает журнал,
`replay-event` делает dry-run или безопасно повторяет одну клетку, не перетирая более
новое состояние. Ручная коррекция пишется отдельным `owner_override` event.

### 5.3. Контекст оценки

Главная техническая проблема: результаты живут **по строковому имени**, а ачивки — по `user_id`.
Нужен один слой перевода, иначе `find_user_by_name` вызовется в каждом правиле для каждого игрока
(N+1 к БД).

```python
@dataclass
class TournamentContext:
    tournament: models.Tournament
    history: AchievementHistory                   # история игроков с кэшами на прогон
    participants: dict[int, models.Participant]   # user_id -> participant (все, включая чужие записи)
    users: dict[int, models.User]
    eligible_user_ids: set[int]                   # прошли все requirements текущего lifetime ruleset
    records: dict[int, PlayerRecord]              # user_id -> wins/losses/draws/rounds
    undefeated_user_ids: set[int]
    skipped: list[SkippedPlayer]                  # кто и почему не в зачёте — идёт в отчёт
```

Собирается один раз в `build_context()`: имена из canonical read-only match projection →
`UserService.find_by_name()` без merge/create, с кэшом
name→user → `user_id`. Правила получают готовый контекст и ходят в БД только через
`AchievementHistory` (счётчик колод, серия посещений, деки за 90 дней) — там тоже кэш на прогон.

### 5.4. Правила

Правило возвращает и выдачи, и обновления прогресса, и **причины** — человекочитаемые факты из
истории, которые попадут в сообщение.

```python
@dataclass
class Award:
    user_id: int
    code: str
    level: int
    progress_value: int | None
    evidence: str                 # «4-0 на Elves; всего X-0 турниров: 3»

@dataclass
class ProgressUpdate:
    user_id: int
    code: str
    value: int                    # стало (previous читается из БД при записи)
    threshold: int                # порог следующего уровня
    next_level: int
    evidence: str                 # «Mono Red Madness (17.07), Elves (24.07)»

@dataclass
class RuleOutcome:
    awards: list[Award]
    progress: list[ProgressUpdate]

class AchievementRule(Protocol):
    code: str
    requirements: DataRequirements
    def evaluate(self, ctx: TournamentContext) -> RuleOutcome: ...
```

Семь классов: `DebutRule`, `FirstDeckRule`, `UndefeatedRule`, `ScribeRule`, `RegularRule`,
`MulticlassRule`, `LoyalistRule`. Все счётчики наследуют `CounterRule` — она превращает значение в
взятые уровни и прогресс до следующего. Каждое правило — чистая логика от контекста и БД,
тестируется без Telegram.

### 5.5. Сервис

```python
class AchievementService:
    def __init__(self, db, rules=None, history=None) -> None: ...

    def evaluate_for_tournament(self, tournament_id: int) -> tuple[TournamentContext | None, RuleOutcome]:
        """Прогнать все правила по завершённому турниру. В БД ничего не пишет.
        None вместо контекста — турнира нет или он ещё не полон."""

    def apply(self, ctx, outcome, *, notified: bool = False) -> AppliedResult:
        """Идемпотентно записать выдачи и обновить прогресс.
        Возвращает ТОЛЬКО реальные изменения: новые ачивки и прогресс, значение которого сдвинулось."""

    def process_tournament(self, tournament_id: int, *, notified: bool = False) -> AppliedResult | None:
        """evaluate + apply. Безопасно вызывать повторно: второй раз результат пустой."""

    def list_for_user(self, user_id: int) -> list[AchievementView]:
        """Все определения + получено/в процессе/закрыто + прогресс — для UI."""

    def unnotified_for_tournament(self, tournament_id: int) -> list[models.UserAchievement]
    def mark_notified(self, achievements: list[models.UserAchievement]) -> None
```

`AppliedResult` — то, из чего строится отчёт владельцу: `granted`, `progress_changes`, `skipped`
(кто играл, но в зачёт не попал — это полезно видеть).

Сбой одного правила не роняет остальные: ачивки не должны стоить нам турнира. Каждый завершённый
расчёт сохраняется в `achievement_processing_runs` со статусом `completed`, `partial` или `failed`,
счётчиками и безопасным списком `code + exception type`. Текст исключения в DB/Telegram/JSON не
попадает. При `partial/failed` owner видит предупреждение в отчёте.

`backfill()` — фаза 2, ещё не реализован.

### 5.6. Точки вызова

1. **Основная:** `bot/scheduler.py:maybe_announce_meta_gather_completed()` — шаг 4, сразу после
   `close_tournament()`. Там турнир гарантированно завершён, полон и все колоды записаны. Вызов
   best-effort в `try/except` — падение ачивок не роняет анонс (тест на это есть).
2. **Ручная:** CLI `python3 cli.py achievements process <tournament_id>` — перевыдача после правок
   правил.
3. **Бэкафилл:** CLI, см. фазу 2 (не реализовано).

Все идемпотентны, порядок вызовов значения не имеет.

## 6. Режимы видимости и уведомления

### 6.1. Три режима

Ачивки въезжают в прод в теневом режиме и переключаются по мере готовности. Режим — один
feature flag + один резолвер получателя, а не три разных кодовых пути.

| Режим | Движок считает | Кто видит `/achievements` | Кому уходят уведомления |
|---|---|---|---|
| **shadow** (старт) | да, на каждом завершённом турнире | только владелец и админы (команда скрыта из `/help`) | **владельцу, одним агрегированным сообщением на турнир** |
| **beta** | да | владелец, админы и игроки из белого списка | владельцу |
| **public** | да | всем | каждому игроку — своё, только по opt-in |

Реализация:

```python
class FeatureFlags:
    ACHIEVEMENTS = "achievements"           # движок считает и пишет в БД
    ACHIEVEMENTS_PUBLIC_UI = "achievementsPublicUi"     # /achievements доступна игрокам
    ACHIEVEMENTS_PLAYER_DM = "achievementsPlayerDm"     # уведомления уходят самим игрокам
```

Маршрутизация получателя — **одно место**: `send_achievements_report()` в
`bot/telegram/achievements.py`. Owner и player получают независимые outbox rows/statuses;
player batch создаётся только при одновременных global flag, персональном
`notify_achievements` и `notify_allowed_ids`. Opt-out перед retry отменяет pending row.

> ⚠️ Включение `ACHIEVEMENTS_PLAYER_DM` = новый путь массовой рассылки DM реальным людям. По
> правилам проекта (`CLAUDE.md`, notification safety) оно требует **явного подтверждения
> владельца** и сначала проверяется в debug-окружении, где `settings.notify_allowed_ids`
> ограничивает адресатов тремя id.

### 6.2. Агрегированный отчёт владельцу (режим shadow)

Одно сообщение на турнир, а не по сообщению на игрока. Структура: что выдано → у кого сдвинулся
прогресс → кто не попал в зачёт. Везде — **причины из истории**, а не голые цифры.

```
🏅 Ачивки · Pauper 24.07.2026 (Goldfish)
Выдано 3 · прогресс у 5 · не в зачёт 2

НОВЫЕ АЧИВКИ
🎖 Бабаев Михаил — Дебют
   первая своя колода: Mono Red Madness
🏆 Иванов Пётр — Без поражений I
   4-0 на Elves · это его 1-й X-0
📅 Сидоров Иван — Завсегдатай I
   4 турнира подряд в Goldfish: 03.07 · 10.07 · 17.07 · 24.07

ПРОГРЕСС
🎭 Бабаев Михаил — Мультикласс I: 2/3 деки за 90 дней (+1)
   Mono Red Madness (17.07) · Elves (24.07)
🧙 Петров Пётр — Метаписец I: 7/10 чужих колод (+3)
   записал сегодня: Иванов, Сидоров, Кузнецов
📅 Иванов Пётр — Завсегдатай I: 3/4 турнира подряд (+1)
   10.07 · 17.07 · 24.07

НЕ В ЗАЧЁТ
Кузнецов Алексей — колоду записал не он
Смирнов Олег — колода не записана
```

Технические детали отправки:

- лимит сообщения Telegram — **4096 символов**; отчёт режем по секциям на несколько сообщений,
  а не обрезаем молча (в конце — «и ещё N игроков»);
- выдачи, progress snapshots и текстовые сообщения outbox сохраняются одной транзакцией в
  `achievement_report_deliveries`;
- расчёт и owner-доставка одного турнира защищены межпроцессным DB lease в
  `achievement_processing_leases`: конкурентный worker промолчит, а lease аварийно завершившегося
  процесса можно перехватить после expiry;
- отправка best-effort в `try/except`: сбой отчёта не роняет анонс турнира, недоставленная часть
  остаётся `pending` и повторяется при следующем вызове `send_achievements_report()`;
- части длинного отчёта отмечаются отдельно: retry продолжает с первого недоставленного сообщения
  и не повторяет уже успешно отправленные части;
- `notified_at` проставляется только после доставки всех текстовых частей отчёта; карточки остаются
  декоративными и best-effort;
- каждый завершённый расчёт имеет DB audit row с версией движка, временем, итоговыми счётчиками и
  ошибками правил; эта строка коммитится атомарно с выдачами и outbox;
- если новых ачивок и изменений прогресса нет — сообщение не шлём вообще (тишина = «всё посчитано,
  нового нет»).

#### Журнал финальных отчётов

Каждый непустой owner-отчёт до отправки в Telegram атомарно записывается отдельным JSON-файлом:

```text
logs/achievements/tournament-<id>-<UTC timestamp>.json
```

Каталог на production/debug отдельный для каждого deployment working directory, игнорируется git
и сохраняется между штатными deploy: архив распаковывается поверх текущей директории без её
очистки. Путь можно переопределить через `ACHIEVEMENT_LOG_DIR`; пустая строка отключает запись.

Файл содержит точные Telegram-сообщения и структурированные секции `granted`,
`progress_changes`, `skipped`: `user_id`, код/уровень, старое и новое значение, порог,
evidence и причину пропуска. Ошибка файловой записи логируется, но не блокирует owner-отчёт.

Послетурнирная проверка выполняется read-only:

1. Найти JSON по `tournament_id` и зафиксировать все строки выдач/прогресса/пропусков.
2. Сверить `granted` с `user_achievements` по `(user_id, code, level, tournament_id)`, включая
   `evidence` и `notified_at`.
3. Сверить `progress_changes` с `user_achievement_progress` по `(user_id, code)`: `value`,
   `tournament_id`, `evidence`.
4. Для `skipped` проверить участника, реальный `tg_id`, записанную колоду и
   `deck_added_by_tg_id`: причины должны совпадать с гейтом зачёта.
5. Перепроверить паринги и исторические турниры, от которых зависит конкретное правило.

На production во время аудита не вызывать `process_tournament()`/CLI `process`: они записывают
результат. Использовать SQL/ORM-чтение и чистую оценку правил, если требуется пересчёт ожидания.

Реализация по слоям проекта: `bot/handlers/achievements.py` (чистая логика → `HandlerResult`,
покрыта тестами) + `bot/telegram/achievements.py` (тонкая обёртка) + строки в `bot/messages/`.

- юнит на каждое правило — минимум 3 кейса: выдаётся, не выдаётся, краевой;
- гейт §2.5: колоду записал админ → ни выдачи, ни прогресса, игрок попал в «не в зачёт»;
- идемпотентность: `process_tournament` дважды → второй раз пустой `AppliedResult`;
- прогресс: дельта считается от сохранённого значения, а не от нуля;
- скользящее окно «Мультикласса»: прогресс упал, но выданная ачивка осталась;
- контекст: имя из парингов не сматчилось → игрок пропущен, не падаем;
- плейсхолдер (`tg_id < 0`) не получает ачивок;
- незавершённый турнир не выдаёт ничего;
- отчёт: пустой результат → сообщение не отправляется; длинный отчёт → корректно режется;
- маршрутизация: при выключенном `achievementsPlayerDm` единственный адресат — владелец.

## 10. Риски

| Риск | Чем плохо | Как гасим |
|---|---|---|
| Матчинг имён ошибётся | ачивка уйдёт не тому | берём только уверенное совпадение `find_user_by_name`; не сматчилось — игрок пропущен; есть ручное слияние дублей |
| Повторный импорт вечера | дубли / преждевременная выдача | выдаём только на завершённом и полном турнире; unique-ключ; прогресс — снапшот, а не инкремент |
| Случайная рассылка игрокам | спам реальным людям | в shadow единственный адресат — `OWNER_CHAT_ID`; путь к игрокам закрыт флагом; включение требует подтверждения |
| Гейт §2.5 выглядит как баг | «я был 4-0, где ачивка?» | в отчёте секция «не в зачёт» с причиной; при публичном запуске — та же формулировка игроку |
| Скользящее окно «Мультикласса» | прогресс «упал», игрок в непонимании | выданное не отзываем; в тексте прямо пишем «за 90 дней» |
| Падение движка ломает анонс | нет отбивки в чате | вызов best-effort в `try/except`, анонс важнее ачивок |
| Отчёт длиннее лимита Telegram | обрезанное сообщение | режем по секциям на несколько сообщений + «и ещё N» |

## 11. Что дальше (техническая возможность обозначена, детали — позже)

- **«Еретик»** (3-1 на деке вне топ-меты) — динамический недельный top-10 уже есть; перед возвратом
  правила нужно сохранять исторический snapshot на дату турнира, чтобы последующие обновления
  `Archetype.meta_rank` не меняли задним числом, была ли колода вне топа.
- **H2H-ачивки через DataLens** («Злейший враг», «Реванш», «Полиглот»): `winrate_vs_opponents()`
  уже отдаёт список оппонентов с винрейтом. Обязательна механика **топ-3 кандидатов** (иначе квест
  невыполним — нужный человек не придёт), плюс кэш: DataLens внешний и небыстрый.
- **Матчап-ачивки** («Проклятый матчап», «Коллекционер скальпов»): `winrate_vs_opponent_decks()`;
  засчитывать только матчи, где архетип оппонента известен.
- **Сезоны**: отдельная таблица не нужна — «сезон» = период (`Period.last_months(n)` в DataLens /
  фильтр по дате в своей БД). Нужно договориться о границах (месяц или квартал).
- **Рейтинг силы** для «Гигантоубийцы» и лидербордов: полноценный Elo дорог; дешёвый прокси —
  винрейт + объём матчей за период.
- **Лидерборды и «Зал славы»**: поверх уже выданных `UserAchievement` — самый дешёвый следующий шаг.
- **Донор / дерби**: движок «встречных квестов» — самая дорогая механика, ставим последней.
