# Система ачивок — детальный план

Дизайн-документ. Ничего из описанного ещё не реализовано. Цель — довести ачивки от «идеи» до
пошагового плана, где первые фазы проверены на техническую исполнимость по фактическому коду, а
дальние — обозначены как направление.

Контекст и каталог идей (зачем это вообще): [`ideas_engagement.md`](ideas_engagement.md) и
[`ideas_engagement_v2.md`](ideas_engagement_v2.md).

---

## 0. Принципы

1. **Ачивка = топливо маховика данных.** Игрок сам записался → бот знает его результаты → бот даёт
   ему ачивки и статистику → игрок возвращается и записывается снова. Поэтому в первой пятёрке
   обязательно есть ачивки, награждающие именно *саморегистрацию* и *запись чужих колод*.
2. **Не выдаём то, что не можем честно посчитать.** Любая ачивка первой фазы считается только по
   данным собственной БД (`RoundPairing` + `Participant` + `Tournament`). Без DataLens, без
   архетипа оппонента, без внешних сервисов — эти источники подключаем позже и отдельно.
3. **Идемпотентность важнее красоты.** Импорт AetherHub повторяется много раз за вечер, джобы
   перезапускаются. Выдача ачивки должна быть безопасна при любом числе повторных вызовов.
4. **Уведомления — последняя фаза, не первая.** Ачивки должны сначала «настояться» на истории
   (бэкафилл), и только потом включаться рассылки, иначе первый же запуск разошлёт сотни DM.
5. **Одна фаза = один PR = работающий инкремент**, который можно смотреть в проде и не стыдно
   откатить.

| Общее имя колоды | `Archetype.general_name` + `services/deck_mapping.py` | схлопывание вариантов одной деки |

| Рассылка DM с гейтами | `bot/telegram/round_notify.py` (opt-in `User.notify_opponent_rounds` + `settings.notify_allowed_ids`) | образец безопасной рассылки |

## 2. Ограничения данных — что можно и чего нельзя в первых фазах

Можно честно посчитать уже сейчас:

- собственный результат в турнире (W-L-D, место, X-0);
- счёт конкретного матча (2-0 / 2-1) — из `player_wins`/`opponent_wins`;
- собственную колоду и её историю по турнирам;
- участие/посещаемость по клубам и датам;
- кто записал колоду (свою/чужую).

Нельзя (и поэтому не берём в первые фазы):

- **архетип оппонента** — известен, только если оппонент зарегистрирован и колода записана; иначе
  ачивки типа «Проклятый матчап»/«Зеркальщик» молча не срабатывают;
- **порядок игр внутри матча** — «камбек после 0-1» не отличить от 2-1 в другом порядке. Матч 2-1
  честно называть «в трёх играх», а не «камбек»;
- **личность оппонента как игрока бота** — импортные плейсхолдеры (`tg_id < 0`) это люди без
  аккаунта, победа над ними не атрибутируется им;
- **сезоны и рейтинг силы** — их нет; для «Гигантоубийцы» нужен отдельный слой (§10);
- **актуальный топ меты из `meta_rank`** — сид от апреля 2026, руками не обновляется (§3.5).

## 3. Первые 5 ачивок

Все пять считаются **только по собственной БД**. Каждая описана как: правило → источник данных →
краевые случаи.

Общие правила выдачи для всех:

- получатель — только реальный аккаунт (`User.tg_id > 0`); плейсхолдеры импорта пропускаем;
- турнир учитывается, только если он завершён и полон (`is_tournament_complete()`), иначе
  промежуточный импорт мог бы выдать «X-0» после первого раунда;
- ачивка выдаётся один раз (пара `user_id + code + level`), повторная оценка ничего не меняет.

### 3.1. 🎖 Дебют (`debut`)

**Правило:** игрок **сам** записал свою колоду на турнир впервые.

- Источник: `Participant` (`user_id`, `archetype_id IS NOT NULL`,
  `deck_added_by_tg_id == user.tg_id`), сортировка по `Tournament.started_at`/`created_at`.
- Выдаётся в том турнире, где это случилось впервые.
- Краевые: колоду записал админ или оппонент → **не выдаём** (награждаем именно саморегистрацию —
  это цель №2); у игрока может не быть парингов вообще (не пришёл) — всё равно выдаём, действие
  совершено.
- Зачем: мгновенный дофамин в первую минуту знакомства с ботом.

### 3.2. 🏆 Без поражений (`undefeated`, уровни I/II/III)

**Правило:** турнир пройден без поражений и ничьих (X-0), сыграны все раунды.

- Источник: `AetherhubImportService.get_undefeated_players(tournament_id)` — готовый список, уже
  используется в отбивке «сбор метагейма завершён».
- Уровни: **I** — первый раз, **II** — 3 раза, **III** — 10 раз (счётчик по всем турнирам).
- Краевые: **бай считается победой** — так уже работает `_player_records()` и отбивка в чате;
  расходиться с ней нельзя, иначе игрок увидит себя в списке X-0 без ачивки.

### 3.3. 🧙 Метаписец (`scribe`, уровни I/II/III)

**Правило:** записал N **чужих** колод суммарно за всё время. Уровни: 10 / 25 / 50.

- Источник: `Participant.deck_added_by_tg_id == user.tg_id AND Participant.user_id != user.id`.
- Рядом уже есть `RatingService.count_decks_added_by()` — но он считает и свои колоды, нужен
  вариант с фильтром «чужие» (переиспользовать сервис, добавив параметр).
- Зачем: прямая награда за то, что физически наполняет базу данными. Самая «полезная для проекта»
  ачивка из пяти.

### 3.4. 📅 Завсегдатай (`regular`, уровни I/II/III)

**Правило:** участие в N подряд идущих турнирах своего клуба. Уровни: 4 / 8 / 16.

- Источник: `Participant` × `Tournament(club, started_at)`. Берём все завершённые турниры клуба по
  возрастанию даты, строим бинарную цепочку присутствия игрока, считаем текущую серию.
- Клуб игрока = клуб турнира, в котором он играл; серии считаем **отдельно по каждому клубу**.
- Краевые: турниры без `club` игнорируем; отменённый/пустой турнир (нет парингов) не разрывает
  серию — из цепочки его исключаем.
- Зачем: посещаемость и возвращаемость.

### 3.5. 🃏 Еретик (`heretic`)

**Правило:** результат не хуже X-1 (доля побед ≥ 75 % при ≥ 3 сыгранных матчах) на архетипе **вне
текущего топ-8 меты**.

- Источник: результат — из `_player_records()`; архетип — `Participant.archetype`.
- **Топ меты считаем динамически**, а не по `Archetype.meta_rank`: сид `utils/seed.py` заполнен
  топ-10 на апрель 2026 и руками не обновляется — на нём ачивка через полгода станет враньём.
  Динамика: `GROUP BY Archetype.general_name` по участникам турниров клуба за последние 90 дней,
  топ-8 по числу пилотов. Результат кэшируем на время оценки турнира.
- Краевые: у архетипа нет `general_name` → берём `Archetype.name`; кастомные архетипы
  (`is_custom`) в расчёте топа не участвуют, но получить за них ачивку можно.
- Зачем: единственная ачивка из пяти, которая реально двигает разнообразие меты.

> **Если хочется, чтобы первая фаза была совсем дешёвой** — «Еретик» единственная из пяти, кто
> требует нового расчёта (топ меты). Её можно заменить на «Мультикласс» (3 разных архетипа за 90
> дней — чистый `GROUP BY` по `Participant`) или «Полиглот» (25 разных оппонентов — по
> `RoundPairing`). Обе считаются одним запросом и не требуют новых сервисов.

## 4. Модель данных

Одна новая таблица. Определения ачивок живут **в коде** (как `KNOWN_FLAGS` в feature flags) — их
не редактируют из UI, они версионируются вместе с логикой.

```python
class UserAchievement(Base):
    """Выданная игроку ачивка. Одна строка = (игрок, код, уровень) навсегда."""

    __tablename__ = "user_achievements"

    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)
    code = Column(String(32), nullable=False)          # "undefeated"
    level = Column(Integer, nullable=False, default=1) # 1/2/3 для многоуровневых
    tournament_id = Column(Integer, ForeignKey("tournaments.id", ondelete="SET NULL"), nullable=True)
    progress_value = Column(Integer, nullable=True)    # значение счётчика на момент выдачи (10 колод, серия 8)
    awarded_at = Column(DateTime, default=utc_now, nullable=False)
    notified_at = Column(DateTime, nullable=True)      # NULL = ещё не сообщили игроку

    __table_args__ = (UniqueConstraint("user_id", "code", "level", name="uq_user_achievement"),)
```

Плюс поле в `User` (для фазы 4):

```python
notify_achievements = Column(Boolean, default=False, nullable=False, server_default="false")
```

**Миграция:** одна, `down_revision` = текущий head (`7c178567f22c` на момент написания — перед
генерацией проверить: `DATABASE_URL="sqlite:///:memory:" python3 -m alembic heads`). Revision id
генерировать: `python3 -c "import uuid; print(uuid.uuid4().hex[:12])"` — плейсхолдеры вроде
`a1b2c3d4e5f6` переиспользовать нельзя (`tests/test_migrations.py` это ловит).

Уникальный ключ `(user_id, code, level)` — и есть механизм идемпотентности: повторная оценка
турнира не создаст дубль.

## 5. Движок

### 5.1. Структура файлов

```
services/achievements/
    __init__.py        # публичный экспорт: AchievementService, ACHIEVEMENTS
    definitions.py     # реестр AchievementDef (код, название, описание, уровни, редкость)
    context.py         # TournamentContext — все данные турнира, загруженные один раз
    rules.py           # правила: класс на ачивку, метод evaluate(ctx) -> list[Award]
    service.py         # AchievementService: оценка, выдача, чтение, бэкафилл
```

Сервисы оформляем классами с зависимостями в `__init__` (как `RoundNotificationService`,
`StandingsImageService`) — это принятый в проекте стиль.

### 5.2. Определения

```python
@dataclass(frozen=True)
class AchievementDef:
    code: str            # "undefeated"
    level: int           # 1
    title: str           # "Без поражений"
    icon: str            # "🏆" — для текстового UI
    description: str     # «Пройти турнир без единого поражения»
    hint: str            # что сделать, чтобы получить (для «ещё не открыто»)
    rarity: str          # "common" | "rare" | "epic" — влияет только на цвет бейджа
    threshold: int | None = None  # 3 турнира X-0 / 10 колод — для прогресса

ACHIEVEMENTS: dict[tuple[str, int], AchievementDef] = {...}
```

### 5.3. Контекст оценки

Главная техническая проблема: сейчас все результаты живут **по строковому имени**, а ачивки — по
`user_id`. Значит нужен один слой перевода, а не `find_user_by_name` в каждом правиле (это N+1 к БД
на каждого игрока каждого правила).

```python
@dataclass
class TournamentContext:
    tournament: models.Tournament
    participants: dict[int, models.Participant]        # user_id -> participant
    records: dict[int, PlayerRecord]                   # user_id -> wins/losses/draws/rounds
    undefeated_user_ids: set[int]
    meta_top: set[str]                                 # general_name топ-8 меты (для «Еретика»)
```

Собирается один раз в `AchievementService.evaluate_for_tournament()`:
имена из `_player_records()` → `find_user_by_name()` (батчем, с кэшом name→user) → `user_id`.
Правила получают готовый контекст и **не ходят в БД за результатами** — только за своей
исторической агрегацией (счётчик колод, серия посещений).

### 5.4. Правила

```python
class AchievementRule(Protocol):
    code: str
    def evaluate(self, ctx: TournamentContext) -> list[Award]: ...

@dataclass
class Award:
    user_id: int
    code: str
    level: int
    progress_value: int | None = None
```

Пять классов: `DebutRule`, `UndefeatedRule`, `ScribeRule`, `RegularRule`, `HereticRule`. Каждый —
чистая функция от контекста и БД, тестируется отдельно без Telegram.

### 5.5. Сервис

```python
class AchievementService:
    def __init__(self, db: Session, rules: list[AchievementRule] | None = None) -> None: ...

    def evaluate_for_tournament(self, tournament_id: int) -> list[Award]:
        """Прогнать все правила по завершённому турниру. Ничего не пишет в БД."""

    def grant(self, awards: list[Award], *, notified: bool = False) -> list[models.UserAchievement]:
        """Идемпотентно записать выдачи. Возвращает только реально новые строки."""

    def award_for_tournament(self, tournament_id: int, *, notified: bool = False) -> list[models.UserAchievement]:
        """evaluate + grant. Безопасно вызывать повторно."""

    def list_for_user(self, user_id: int) -> list[UserAchievementView]:
        """Все определения + флаг «получено» + прогресс — для UI."""

    def progress_for_user(self, user_id: int, code: str) -> tuple[int, int] | None:
        """(текущее, порог) для многоуровневых — «7/10 колод»."""

    def backfill(self, *, club: str | None = None, dry_run: bool = True) -> BackfillReport:
        """Прогнать по всем завершённым турнирам истории. Выдачи помечаются notified=True."""
```

### 5.6. Точки вызова

1. **Основная:** `bot/scheduler.py:maybe_announce_meta_gather_completed()` — сразу после успешного
   `close_tournament()` (строка ~625). Там турнир гарантированно завершён, полон и все колоды
   записаны. Вызов best-effort в `try/except` — падение ачивок не должно ронять анонс.
2. **Ручная:** админская кнопка на карточке архивного турнира / команда CLI
   `python3 cli.py achievements award <tournament_id>` — для перевыдачи после правок правил.
3. **Бэкафилл:** отдельная CLI-команда, см. фазу 2.

Все три идемпотентны, порядок вызовов значения не имеет.

## 6. Уведомления

> ⚠️ **Это единственная часть плана, которая рассылает сообщения многим людям.** По правилам
> проекта (`CLAUDE.md`, раздел «Notification safety») любой новый код, вызывающий
> `bot.send_message` в цикле по нескольким пользователям, требует **явного подтверждения
> владельца перед выкаткой**. Фаза 4 не начинается без этого подтверждения.

Конструкция копирует уже работающую и проверенную схему `bot/telegram/round_notify.py`:

1. **Opt-in на пользователя** — `User.notify_achievements`, по умолчанию **выключено**, тумблер в
   `/settings` (рядом с «Уведомления об оппоненте»).
2. **Гейт окружения** — `settings.notify_allowed_ids` (в debug рассылка уходит только трём id из
   `config/debug.py`; в prod `None` = всем).
3. **Идемпотентность доставки** — `UserAchievement.notified_at`: шлём только строки с `NULL`,
   проставляем время после успешной отправки. Повторный запуск джобы ничего не продублирует.
4. **Батч на игрока** — если за турнир игрок получил 3 ачивки, это **одно** сообщение (или одна
   картинка-альбом), а не три.
5. **Бэкафилл не уведомляет** — исторические выдачи пишутся сразу с `notified_at = awarded_at`.
   Это защита от «первый запуск разослал 200 писем».
6. **Отладка** — по образцу `send_debug_round_notifications`: команда шлёт **только самому
   запросившему** его собственные ачивки, никогда чужие.

Черновик текста:

```
🏆 Без поражений

Ты прошёл «Pauper 24.07.2026» со счётом 4-0 — ни одного поражения.
Это твой второй такой турнир. Ещё один — и откроется «Без поражений II».

Открыто ачивок: 5 из 12 · /achievements
```

Где ещё показывать (без DM, безопасно):
- в отбивке «сбор метагейма завершён» в чат клуба — одна строка «🏅 Сегодня открыто 7 ачивок,
  свои смотри в /achievements» (агрегат, никаких персональных данных и никаких рассылок);
- в карточке турнира и в `/settings` — подсказка про команду.

### 7.2. Картинки (фаза 3)

Рисуем на PIL в том же визуальном языке, что стендинги и график меты (`services/chart_style.py`:
тёмный градиент, кремовый текст, золотой акцент, шрифты DejaVu).

**Важное техническое ограничение:** в DejaVu **нет эмодзи** — 🏆 и 🧙 отрисуются квадратами-тофу
(это уже известно, см. комментарий про клубы в `chart_style.py:30`). Поэтому иконку бейджа
**нельзя** просто нарисовать эмодзи-символом. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Генеративный бейдж примитивами PIL** (круг с градиентом по редкости, кольцо, монограмма-буква/римская цифра уровня) | без внешних ассетов, единый стиль, ноль зависимостей — начинать с него | «геометрично», не иллюстрация |
| B. Заранее нарисованные PNG в `assets/badges/<code>.png` | красиво и уникально | нужен художник/генерация картинок руками |
| C. Шрифт Noto Color Emoji + `embedded_color=True` | эмодзи «как в телефоне» | +9 МБ шрифт в репо, капризная отрисовка |

Рекомендация: **A** в фазе 3, **B** — когда появятся нарисованные иконки (подменяется одним
методом, интерфейс не меняется).

Два макета:

1. **Карточка одной ачивки** (1179 × ~640) — для момента выдачи: медальон слева, справа название
   золотым `DejaVuSerif-Bold 56`, описание `DejaVuSans 32`, снизу «Игрок · Турнир · Дата»,
   тонкая рамка цвета редкости.
2. **Полка ачивок** (1179 × высота по числу рядов) — для `/achievements`: сетка бейджей 3 в ряд,
   открытые в цвете, закрытые затемнённые (25 % прозрачности) с подписью прогресса «14/25».

Ограничения Telegram, которые нужно учесть в отправке: подпись к фото ≤ 1024 символов, альбом ≤ 10
элементов — обе константы уже есть в `bot/scheduler.py` (`_TG_CAPTION_LIMIT`, `_TG_ALBUM_LIMIT`),
переиспользовать их, а не заводить новые.

Тестировать картинки как `tests/test_bot_chart.py`: проверяем, что рендер возвращает валидный PNG
непустого размера, и что раскладка не падает на краевых данных (длинное имя, 0 ачивок, все
открыты).

## 9. Тесты

Стиль проекта: SQLite in-memory, без Telegram-моков, тестируем `handle_*` и сервисы.

- юнит на каждое правило — минимум по 3 кейса: выдаётся, не выдаётся, краевой;
- идемпотентность: `award_for_tournament` дважды → второй раз ноль новых;
- контекст: имя из парингов не сматчилось с аккаунтом → игрок просто пропущен, не падаем;
- плейсхолдер (`tg_id < 0`) не получает ачивок;
- незавершённый турнир (`is_tournament_complete() == False`) не выдаёт ничего;
- рендер картинок: валидный PNG, длинные имена, пустой список;
- уведомления: opt-in/opt-out, гейт `notify_allowed_ids`, `notified_at`.

## 10. Риски

| Риск | Чем плохо | Как гасим |
|---|---|---|
| Матчинг имён ошибётся | ачивка уйдёт не тому | берём только уверенное совпадение `find_user_by_name`; не сматчилось — игрок просто пропущен; есть ручное слияние дублей |
| Повторный импорт вечера | дубли/преждевременная выдача | выдаём только на завершённом и полном турнире; unique-ключ `(user_id, code, level)` |
| Первый запуск рассылок | сотни DM реальным людям | бэкафилл до уведомлений + `notified_at` + opt-in + гейт окружения + подтверждение владельца |
| `meta_rank` устарел | «Еретик» врёт | динамический топ меты за 90 дней, а не сид |
| Ачивка невыполнима без данных оппонента | молчаливая несправедливость | в первой пятёрке таких нет; в 🟡-фазе показывать причину «не засчитано» |
| Спам уведомлениями | выгорание, отписки | один батч на игрока за турнир, opt-in по умолчанию выключен |
| Падение движка ломает анонс | нет отбивки в чате | вызов best-effort в `try/except`, анонс важнее ачивок |

## 11. Что дальше (техническая возможность обозначена, детали — позже)

- **H2H-ачивки через DataLens** («Злейший враг», «Реванш», «Полиглот»): `winrate_vs_opponents()`
  уже отдаёт список оппонентов с винрейтом — «злейший враг» = минимальный винрейт при ≥ N матчей.
  Обязательна механика **топ-3 кандидатов** (иначе квест невыполним — нужный человек не придёт),
  плюс кэш: DataLens внешний и небыстрый.
- **Матчап-ачивки** («Проклятый матчап», «Коллекционер скальпов»): `winrate_vs_opponent_decks()`
  даёт винрейт против архетипов; засчитывать только матчи, где архетип оппонента известен.
- **Сезоны**: отдельная таблица не нужна — «сезон» выражается периодом
  (`Period.last_months(n)` в DataLens / фильтр по дате в своей БД). Достаточно договориться о
  границах (календарный месяц или квартал).
- **Рейтинг силы** для «Гигантоубийцы» и лидербордов: полноценный Elo дорог; дешёвый прокси —
  винрейт + объём матчей за период из DataLens.
- **Лидерборды и «Зал славы»**: поверх уже выданных `UserAchievement` — самый дешёвый следующий
  шаг после фазы 4.
- **Донор / дерби**: требует движка «встречных квестов» (у кого на кого открыт квест) — самая
  дорогая механика из всего списка, ставим последней.
