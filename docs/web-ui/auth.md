# Web UI: Authorization Research

## Контекст

Telegram заблокирован в РФ. Цель — дать возможность записаться на турнир людям без Telegram и без VPN. Нужен независимый от Telegram auth.

Telegram Login Widget тоже не подходит — виджет обращается к `oauth.telegram.org`, что заблокировано.

---

## Варианты

### 1. Email + Magic Link (рекомендуется)

Пользователь вводит email → получает письмо с одноразовой ссылкой → кликает → авторизован.

**Как работает:**
- POST `/auth/login` с email → генерируем JWT с TTL 15 мин → отправляем письмо
- GET `/auth/verify?token=...` → проверяем JWT → создаём сессию (httponly cookie)
- Сессия живёт 30 дней, обновляется при активности

**Pros:**
- Не требует Telegram, работает везде
- Нет паролей — нечего утечь, нечего сбрасывать
- Email есть у всех
- Инфраструктура: любой SMTP (Gmail SMTP бесплатно, или Resend/Mailgun)

**Cons:**
- Нужен email-провайдер (небольшая зависимость)
- Если пользователь меняет email — теряет доступ (решается привязкой к tg_id в БД)

**Реализация:** `itsdangerous.URLSafeTimedSerializer` или просто JWT в `user_id:email:timestamp` → HMAC. Без новых библиотек почти.

---

### 2. Регистрационный токен (без аккаунта)

Пользователь заполняет форму (имя + архетип) → система выдаёт уникальный URL для управления записью. Аккаунта нет вообще.

**Как работает:**
- POST `/register` → создаём запись → возвращаем `/my-registration/UUID-TOKEN`
- Токен сохраняем в БД рядом с записью (UUID, не предсказуемый)
- Пользователь сохраняет URL (или получает на email)

**Pros:**
- Максимально просто — нет auth layer вообще
- Нет аккаунтов, нет паролей, нет email-инфраструктуры
- Работает везде

**Cons:**
- Потерял ссылку — потерял доступ (если нет email)
- Нельзя посмотреть "все мои турниры" — нет единого профиля
- Слабая защита: если кто-то угадал UUID — может изменить чужую запись (UUID v4 = 122 бит энтропии, практически невозможно)

**Verdict:** Подходит если нет нужды в профиле пользователя. Очень легко реализовать.

---

### 3. Google OAuth

Стандартный "Войти через Google". Google работает в РФ (пока).

**Pros:**
- Знакомый UX
- Не нужна email-инфраструктура
- Google аккаунт есть почти у всех

**Cons:**
- Зависимость от Google (может быть заблокирован)
- Нужно регистрировать OAuth App в Google Console
- Больше кода (authlib или готовые библиотеки)

**Verdict:** Хороший вариант, но зависимость от внешнего провайдера. Если Google заблокируют — всё сломается.

---

### 4. Логин через ВКонтакте (VK OAuth)

Аналог Google OAuth, но VK точно доступен в РФ.

**Pros:**
- Гарантированно работает в РФ
- VK есть у целевой аудитории (русскоязычные игроки)

**Cons:**
- VK OAuth API немного специфичен
- Не у всех есть VK (или не хотят использовать)
- Зависимость от VK

---

## Рекомендация

**Для MVP: Вариант 2 (регистрационный токен)**

Причина: нет зависимостей, реализуется за 1 час, нет email-инфраструктуры. Пользователь регистрируется и получает ссылку — для записи на турнир этого достаточно.

Опционально: добавить email поле → отправлять ссылку на email. Тогда "потерял ссылку" не проблема.

**Следующий шаг (если нужен профиль): Вариант 1 (Magic Link)**

Чисто и просто. Email-провайдер — минимальная зависимость.

---

## Связь Telegram ↔ Web аккаунтов

Если пользователь существует в боте и также регистрируется через веб — нужна связка. Варианты:
- Поле `telegram_username` при регистрации (user вводит вручную, не верифицируется)
- Или просто не связывать — два независимых потока, данные объединяет организатор

Для MVP — **не связывать**, оставить независимыми.
