# Мета-анализ: ИИ-аналитик метагейма клуба

Статус: локальный план, без реализации и без коммита.

Дата: 18 сентября 2026 года.

## 1. Что это за функция

Owner-only Telegram-команда (скрыта от всех, кроме владельца бота), которая по
выбранному турниру клуба строит аналитический отчёт о метагейме:

1. **Мета прошедших турниров клуба** — распределение архетипов, доли, тренд по окну.
2. **Винрейт игрока по конкретным колодам** — персональный срез внутри клуба.
3. **Внешний контекст** — мировые винрейты и доли из открытых источников: mtgdecks.net,
   позже Magic Oculus (RU-агрегат точек).
4. **ИИ собирает и считает сам** — модель получает набор инструментов для выборки
   внутренних данных и внешних источников и сама оркестрирует вычисления.
5. **Итоговый анализ**:
   - какой колодой стоит прийти на следующий турнир клуба (по винрейтам против ожидаемого пула);
   - какая мета ожидается в следующий раз в клубе;
   - чем мета клуба отличается от мировой (mtgdecks).

Главный принцип: **все числа производит детерминированный код, ИИ их интерпретирует**.
Модель не выдумывает и не экстраполирует цифры — она работает только с тем, что вернули
инструменты, и обязана цитировать источник и объём выборки (`n`).

Функция потенциально платная (премиальный слой). На старте скрыта за feature flag и
доступна только владельцу; архитектура закладывается так, чтобы позже закрыть её подпиской.

```
        │                                  │

        │                     ├─ matchups.py       (локальная H2H-матрица)
        │                     ├─ mapping.py        (локальные ⇄ мировые имена)
        │                     ├─ metrics.py        (EV, дивергенция, forecast)
        │                     └─ report.py         (сборка отчёта из блоков)
        │                                  │
        │                     services/mtgdecks.py        ← внешние данные (порт скрапера)
        │                     services/magicoculus_meta.py ← опционально, позже
        │                                  │
        │                                  ▼
        │                     services/metanalysis/llm/   ← ИИ-слой
        │                     ├─ provider.py   (клиент LLM API; сменяемый)
        │                     ├─ tools.py      (реестр инструментов, grounding)
        │                     └─ analyze.py    (оркестрация, бюджет вызовов, кеш)
        │
        └──► CLI:  python3 cli.py metanalysis ...        ← отладка без LLM и без Telegram
```

Правила слоёв (обязательные для проекта):

- `services/metanalysis/` не импортирует Telegram; принимает `Session` + примитивы.
- Handler в `bot/handlers/metanalysis.py` — чистый, unit-тестируется без моков.
- Обёртка в `bot/telegram/metanalysis.py` — только I/O и `user_data`.
- `services/mtgdecks.py` — единственное место с HTML-скрапингом внешнего сайта.
- LLM-вызовы изолированы в `services/metanalysis/llm/`; провайдер инжектится для тестов.

## 4. Детерминированный слой (без ИИ) — что считать

Все данные считаются из первичных таблиц; источник правды — БД бота.

### 4.1. Срез меты клуба/турнира (`club_meta.py`)

- Вход: клуб, `tournament_id` или окно (дней / число последних турниров).
- Выход: по каждому архетипу — число участий, доля поля (%), тренд (первая половина окна
  против второй), группировка по `general_name` (фоллбек — `name`).
- Учитываются только `closed` турниры. Участники без парингов отбрасываются (как в `season_stats.py`).
- Окно по умолчанию: 90 дней или последние 10 закрытых турниров клуба — настраивается.

### 4.2. Винрейты колод и игроков (`deck_winrates.py`)

Источник матчей — `RoundPairing` / `RoundMatch` с заполненным счётом. Bye и несыгранные
раунды не считаются.

- **Винрейт архетипа** = `W / (W + L)` по матчам в окне, где игрок ходил этой колодой
  (`participant.archetype.general_name`).
- **Винрейт игрока по колоде** = тот же расчёт, но ограничен парой `user ↔ deck`.
- **H2H-матрица клуба** (`matchups.py`) = архетип против архетипа: `(W, L, n, wr%)`.
- Каждая строка несёт `n` и 95%-доверительный интервал (Wilson). Винрейт ниже минимального
  `n` (например, `n < 20` для архетипа, `n < 8` для H2H) помечается недостоверным и в отчёте
  звучит «мало данных», а не «43%».

### 4.3. Маппинг локальных ⇄ мировых имён (`mapping.py`)

Клубные названия («Blue Delver», «Spy», «Jund Midrange») не совпадают с mtgdecks
(«Mono Blue Terror», «Spy Combo», «Jund Wildfire»). Без маппинга сравнение локальной и
мировой меты нечестное.

- Источник истины: явная таблица `local ⇄ mtgdecks` в `services/metanalysis/mapping.py`
  + существующие алиасы `ArchetypeAlias` и `deck_book`.
- Fuzzy-подсказки через `rapidfuzz` — только для ручной проверки, не автоматически:
  неоднозначные или ненайденные пары попадают в quality-отчёт, и решает их владелец.
- «Jund Midrange → Jund Wildfire» — это приближение; в отчёте такие пары честно помечаются
  как «≈ ближайший мировой эквивалент».

### 4.4. Метрики и forecast (`metrics.py`)

- **EV против поля** — «какой колодой прийти»: `EV = Σ(доля соперника × H2H-винрейт колоды)`.
  Непокрытые локальной матрицей пары заполняются мировым винрейтом из mtgdecks (пометка
  «extrapolated»); в отчёте приводится и покрытие поля.
- **Дивергенция с миром**: `Δдоля = доля_локальная − доля_mtgdecks`,
  `Δwr = wr_локальный − wr_mtgdecks`.
- **Forecast «мета в следующий раз»**: recency-взвешенное распределение архетипов клуба +
  сдвиг тренда за окно. Честно помечается как прогноз, а не факт.

## 5. ИИ-слой и инструменты модели

### 5.1. Провайдер — открытое решение (см. §14)

Интерфейс `LLMProvider` с tool-calling (function calling). Стартовые кандидаты:
Anthropic Claude, OpenAI-compatible, Yandex GPT. Провайдер инжектится, модель и ключ
задаются из `Settings` (пустой дефолт; реальные значения только в `bot/.env`).

### 5.2. Инструменты, которые видит модель

Модель не скрейпит сама. Сбор и вычисления — только через зарегистрированные функции:

| Инструмент | Возвращает |
|---|---|
| `club_tournaments(club, limit)` | закрытые турниры клуба (id, дата, title, число участников) |
| `club_meta(club, days | tournament_id)` | доли архетипов с `n` и доверительным интервалом |
| `deck_winrates(club, days)` | винрейты архетипов с `n`, CI, трендом |
| `player_winrate(player_name, deck=None)` | винрейты игрока (все или по конкретной колоде) с `n` |
| `local_matchups(club, days)` | H2H-матрица клуба с `n` |
| `global_meta(source="mtgdecks")` | мировая мета: доля, винрейт, trend, tier |
| `global_matchups(deck)` | мировая H2H-матрица с `n` |
| `weighted_ev(club, tournament_id, deck)` | EV колоды против пула + покрытие поля / extrapolated |
| `meta_divergence(club, days)` | `Δдоля`, `Δwr` локаль ⇄ мир по маппингу |

Каждый инструмент возвращает числа + `n` + окно/дату среза; в ответ добавляется источник
(«internal DB», «mtgdecks.net»). Это анти-галлюцинационный контракт.

### 5.3. Контракт отчёта (grounding)

В системный промпт явно вписано:

- Любое число в отчёте должно прийти из вызова инструмента. Запрещено придумывать
  процент, долю или `n`.
- Оценка без выборки даётся словами («данных мало»), не числом.
- Названия колод должны совпадать с маппингом; приближения помечать.
- Формат отчёта — по шаблону ниже, язык — русский.
- «Прогноз» и «факт» разделяются явно.

### 5.4. Структура отчёта (фиксированный шаблон)

1. Сводка: выбранный турнир/окно, дата анализа, источники.
2. Мета клуба: топ колод по доле, тренд, сравнение с прошлым окном.
3. «Какая колода стоит прийти»: топ по `weighted_ev`, против кого хороша/плоха.
4. «Ожидаемая мета в следующий раз»: forecast + факторы.
5. «Клуб vs мир»: таблица `Δдоля`/`Δwr` по маппингу; уникальные местные колоды отдельно.
6. Винрейт конкретного игрока по колодам (по запросу / опционально).
7. Оговорки: низкие `n`, экстраполяции, приблизительный маппинг.

## 6. Команда и UX (owner-only)

- Команда: `/metanalysis` (`filters=PRIVATE`).
- Feature flag: `metaAnalysis` (default `false`). Команда не отвечает, если флаг выключен
  или инициатор ≠ владелец (`user.id == settings.OWNER_CHAT_ID`).
- Флоу (wizard в `context.user_data`):
  1. Выбор клуба (кнопки: Goldfish, Edinorog, Pair of dice, Калининград, Endstep-ru).
  2. Выбор закрытого турнира этого клуба (последние ~15, даты + число участников).
  3. Запуск анализа.
- **Безопасность рассылки (hard rule):** весь вывод — **только инициатору**, в его chat_id.
  Никаких групповых сообщений и DM другим игрокам. Долгий анализ: сразу placeholder
  («Анализирую…»), результат — тем же сообщением, когда готов. Аналог `/bingo_preview`.
- Вывод: текстовый отчёт (разбиение ≤ 4096 символов) + опционально PNG-диаграммы через
  `services/meta_chart.py`.
- CLI: `python3 cli.py metanalysis run --tournament <id> [--no-llm]` — сначала без LLM
  (только детерминированный слой), `--llm` добавляет текст. Ускоряет отладку.

## 7. Хранение и кеширование

- **Внешние данные**: mtgdecks-срезы кешируются с TTL (~1 ч) в БД (новая таблица
  `external_meta_snapshots`: источник, дата среза, JSON) — идемпотентно, при падении сайта
  используется последний свежий срез.
- **LLM-затраты**: кеш отчётов по ключу `(club, tournament, data_fingerprint, prompt_version)`.
  Повторный запрос с теми же данными не платит повторно.
- **Бюджет вызовов**: лимит tool-calls на анализ, лимит токенов ответа, лимит попыток.
  Стоимость и время одного прогона логируются в Monium (`app_stats`) — до монетизации нужно
  знать себестоимость.
- История отчётов на старте не хранится — решается в §14.

## 8. Этапы внедрения

### Этап 0 — детерминированные срезы (без внешних данных и ИИ)

- Пакет `services/metanalysis/`: `club_meta`, `deck_winrates`, `matchups`, `metrics`
  (EV, дивергенция); новые модели — в `core/schemas.py`.
- Переиспользовать логику `season_stats.py` (closed+scored, отбор по счёту).
- `python3 cli.py metanalysis data --club ... --tournament <id>`.
- Прогнать на реальных закрытых турнирах: coverage пар, число колод, пригодных для винрейта
  (`n ≥ 20`) — сразу видно качество выборки.
- Acceptance: винрейты/доли на тестовом срезе совпадают с ручным подсчётом.

### Этап 1 — внешние источники (mtgdecks)

- Перенести `scripts/dev/mtgdecks_scraper.py` в `services/mtgdecks.py` с кешем, ошибками и
  повторами по образцу `AetherhubService` (`_GET_ATTEMPTS`/backoff).
- Таблица `external_meta_snapshots` + `core/models.py` + Alembic-миграция (свежий `revision
  id`, `down_revision` = текущий head).
- Маппинг `mapping.py` по текущему top-мете Pauper на mtgdecks; проверка владельцем.
- Acceptance: `cli.py metanalysis global --source mtgdecks` отдаёт срез; маппинг покрывает
  ≥ 90% имён из свежего окна меты клуба.

### Этап 2 — ИИ-инструменты

- `services/metanalysis/llm/`: provider (инжектируемый), реестр инструментов, системный
  промпт, контракт отчёта, бюджет/кеш.
- В `core/config.py` — новые `Settings` с **пустыми** дефолтами
  (`METANALYSIS_LLM_API_KEY = ""` и аналогичные); реальные значения только в `bot/.env`.
- Vendor SDK в `requirements.txt`.
- Acceptance: инструмент `weighted_ev` работает на данных этапа 0; контрактный тест —
  модель обязана воспроизвести вычисленные числа (см. §10).

### Этап 3 — Telegram-команда

- Feature flag `metaAnalysis` (default false), `/metanalysis` + wizard (клуб → турнир).
- `bot/handlers/metanalysis.py` + `bot/telegram/metanalysis.py`; регистрация в `main.py`.
- Вывод только инициатору; placeholder; PNG-диаграммы.
- Acceptance: с включённым флагом владелец получает отчёт в личку; для любого другого
  пользователя команда молчит; ничего не рассылается в группы.

### Этап 4 — прогон на реальных турнирах, калибровка

- Прогнать на прошедших турнирах Goldfish / Edinorog / Endstep-ru.
- Сверка: повторяет ли отчёт цифры из детерминированного слоя; помечены ли оговорки.
- Тюнинг промпта, порогов `n`, forecast. Зафиксировать себестоимость прогона.
- Acceptance: отчёт на production-срезе содержит только числа из инструментов (проверка
  по ключевым метрикам), рекомендации совпадают с ручным `weighted_ev`.

### Этап 5 — путь к платному слою (отдельно, потом)

- Премиум-гейт на команду по пользователю (флаг/поле или подписка через ЮKassa).
- Опционально веб-страница отчёта (`web/routes/`) и история анализов.
- В первом PR делается только совместимость: команда owner-only + feature flag, гейт позже
  заменяет проверку «владелец».
- `TODO.md` обновляется в том же PR, который меняет статус этапа или решение.

## 9. Монетизация (контекст, не scope)

- Self-service слой: детерминированные срезы (мета, винрейты, H2H) — потенциальный базовый
  продукт; ИИ-анализ — премиум.
- Доступ с самого начала «один получатель» — легко переключить на подписку.
- Перед включением платного слоя обязательна проверка: себестоимость прогона (Monium),
  лимиты на пользователя, кеш, дневная квота, правила приемлемого использования.

## 10. Тестирование

- **Детерминированный слой**: SQLite in-memory, фикстуры закрытых турниров со счетами;
  сверка винрейтов/H2H/EV руками. Без внешних сайтов и LLM.
- **mtgdecks**: фикстуры HTML (как `docs/aetherhub_formats/`) + тесты парсеров; кеш — с
  фейковым транспортом.
- **Маппинг**: таблица сценариев (точное имя, синоним, опечатка, отсутствует → quality).
- **ИИ-слой**: провайдер-мок; contract test: набор данных → записанный ответ модели → все
  числа из ответа присутствуют во входных данных и совпадают с детерминированными расчётами.
- **Handlers**: `handle_xxx` без моков (паттерн репозитория); wrapper — `AsyncMock`.
- **Секреты**: в тестах только фейковые значения (`"dummy-not-a-real-key"`); ключи не
  печатать в логи/вывод/чат; миграция проверяется `tests/test_migrations.py`.

## 11. Секреты и безопасность

- Единственное место ключей — `bot/.env` и GitHub Action secrets. В git — ничего.
- Новые `Settings` добавляются с пустым дефолтом (правило AGENTS.md).
- LLM-инструменты получают только агрегированные данные; персональные данные не выходят за
  пределы сервера (имена в отчёте — публичные ники/ФИО из стендингов, никаких tg_id в промпт).
- Бюджет вызовов и rate limit — защита от случайного разгона счёта LLM.

## 12. Открытые продуктовые решения

1. **LLM-провайдер и модель.** Anthropic Claude vs OpenAI-compatible vs Yandex GPT; влияет
   на SDK, цену и качество русского текста.
2. **Объект анализа.** Сначала только `tournament_id` (по запросу), а окно клуба — в настройке
   вызова. Подтвердить, что метрики считаются и по окну.
3. **Маппинг имён.** Источник истины и признания погрешности («Jund Midrange ≈ Jund Wildfire»).
   Решение фиксируется в issue.
4. **История отчётов.** Хранить ли результаты (БД/файл/ничего) — влияет на кеш и будущий PR.
5. **Прогноз.** Как глубоко идти в модели forecast: простая recency-взвешенная экстраполяция
   vs полноценная модель. Первая версия — простая + словесная интерпретация ИИ.
6. **Магикулус.** Подключить как источник RU-агрегата сейчас (нужны read-endpoints и агрегация
   на стороне Oculus — межпроектная зависимость) или отложить до появления данных.
7. **Себестоимость и квоты.** Порог затрат на один прогон и дневной лимит — зафиксировать до
   монетизации.
