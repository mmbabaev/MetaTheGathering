# Мониторинг доступности Telegram-ботов

Статус: локальный план, без реализации и без коммита.

Дата: 7 сентября 2026 года.

## Референсный инцидент: отказ общего Telegram-туннеля

### Что произошло

- Production и debug-инстансы MetaGatherer и Cards Order работали на одной VM в Yandex Cloud.
- Прямой доступ VM к Telegram Bot API был недоступен, поэтому все боты использовали общий
  SOCKS5-туннель `127.0.0.1:1080` через внешний VPN/VPS.
- 7 сентября 2026 года примерно в 01:25 МСК SSH-соединение до внешнего узла оборвалось.
- `autossh` остался в состоянии `active`, но не мог заново подключиться к внешнему узлу:
  `Connection timed out`. Локальный SOCKS-порт перестал слушать.
- MetaGatherer ушёл в цикл перезапусков, а Cards Order остался формально `running`, но не мог
  выполнять `getUpdates`. Поэтому простой проверки `systemctl is-active` недостаточно.
- Web API, nginx, PostgreSQL и сама VM продолжали работать. Массового сбоя Yandex Cloud или
  Telegram не было.
- Пока бот не работал, плановая задача создания турнира Edinorog на 12:00 МСК была пропущена.

### Корневая причина и зона поражения

Общая недублированная зависимость всех Telegram-ботов — один SOCKS-туннель. Отказ VPN/VPS или
маршрута до него одновременно лишает связи с Telegram все процессы, даже если VM и systemd
считают их исправными.

### Полезные признаки этого класса аварии

- на `127.0.0.1:1080` нет слушающего сокета;
- запрос к Telegram Bot API через SOCKS не проходит;
- в логах ботов одновременно появляется `httpx.ConnectError: All connection attempts failed`;
- `autossh` многократно пишет `ssh exited with error status 255; restarting ssh`;
- быстро растёт `NRestarts` у MetaGatherer;
- после планового времени в БД отсутствует ожидаемый турнир с slug текущей даты.

## Цель мониторинга

Узнать о потере реальной связи ботов с Telegram не позднее чем через 3–5 минут и получить
уведомление по каналу, который не зависит от Telegram. Отдельно обнаруживать последствия
простоя: пропущенные плановые турниры и другие бизнес-задачи.

## Рекомендуемая схема

### 1. Локальная функциональная проверка на VM — главный сигнал

Раз в минуту systemd timer запускает короткий health-check:

1. Проверяет, что `127.0.0.1:1080` слушает.
2. Делает реальный HTTPS-запрос к Telegram Bot API через SOCKS. Достаточно безопасного `getMe`
   одного служебного бота либо запроса к `https://api.telegram.org` без токена, если нужно
   проверять только транспорт.
3. Проверяет состояния bot-сервисов и рост числа перезапусков.
4. Отправляет heartbeat во внешний сервис мониторинга. При ошибке отправляет fail-сигнал с
   коротким кодом причины: `socks_down`, `telegram_unreachable`, `service_flapping`.

Токены ботов и уникальный URL heartbeat не должны попадать в git или журналы. Они хранятся
только в server environment/credentials.

### 2. Уведомление вне Telegram

Основной вариант для первого этапа: внешний heartbeat/synthetic-сервис с email и push/звонком,
например Better Stack или Healthchecks.io. Критично, чтобы аварийный канал не был Telegram.

Рекомендуемые правила:

- warning после двух подряд ошибок;
- incident через 3 минуты без успешной проверки;
- отдельное уведомление о восстановлении;
- повтор через 15–30 минут, если проблема сохраняется;
- получатели: email и мобильный push владельца; для критического production-сигнала можно
  добавить телефонный звонок.

### 3. Внешняя проверка VM/Web

Внешний монитор раз в минуту проверяет публичный `/health` web-сервиса. Это отдельный сигнал:
он обнаруживает падение VM, nginx, TLS или web-процесса, но не заменяет проверку Telegram через
SOCKS. Желательно, чтобы `/health` проверял БД, но не раскрывал конфигурацию и секреты.

### 4. Проверки бизнес-задач

После каждого ожидаемого времени создания турнира отдельная идемпотентная проверка убеждается,
что в БД существует турнир нужного клуба, даты и slug.

- Проверять через 5 минут после `create_time`.
- Если турнира нет — немедленно alert вне Telegram.
- В сообщении указывать клуб, дату события, ожидаемый slug и безопасную команду/инструкцию для
  ручного catch-up.
- На первом этапе ничего автоматически не создавать: монитор только сообщает.

Аналогичный контроль позже можно добавить для критичных импортов AetherHub и финального
закрытия турнира.

### 5. Ресурсные и системные сигналы

- диск: warning при 85%, critical при 92%; на момент референсного инцидента корень был заполнен
  на 89%, хотя это не стало причиной отказа;
- RAM и OOM kill;
- недоступность PostgreSQL;
- `systemd` restart storm;
- отсутствие heartbeat самого проверяющего timer.

## План внедрения

### Этап 1 — минимальный и быстрый

- Выбрать внешний сервис heartbeat и подключить email + mobile push.
- Добавить на VM health-check Telegram/SOCKS и systemd timer раз в минуту.
- Добавить алерты на отсутствие heartbeat и восстановление.
- Добавить внешний HTTP-check production web.
- Проверить тестовым кратковременным отключением только tunnel-service в согласованное время.

Ожидаемый результат: владелец узнаёт об аналогичном инциденте через 3 минуты, даже если Telegram
полностью недоступен.

### Этап 2 — наблюдаемость приложения

- Публиковать метрики `telegram_connectivity`, `bot_restart_count`, `last_successful_poll_at`,
  `scheduler_job_success_at` и `scheduler_job_failure_total` в уже используемый Monium/OpenTelemetry.
- Создать dashboard и алерты на отсутствие успешного polling и выполнение scheduler jobs.
- Добавить runbook-ссылку в каждый alert.

### Этап 3 — контроль пропущенных задач

- Реализовать монитор ожидаемых турниров на основании живого `club_schedules`.
- Добавить owner-visible журнал запусков scheduler jobs с `started/succeeded/failed/skipped`.
- Продумать отдельный идемпотентный catch-up: после восстановления бот находит пропущенное окно,
  создаёт отсутствующий турнир только при точном совпадении расписания и отсутствии slug.
  Автоматический catch-up включать лишь после периода работы в alert-only режиме.

### Этап 4 — устранение единой точки отказа

- Поднять резервный VPN/VPS в другой сети или у другого провайдера.
- Предпочтительно разрешить SSH-туннель также через порт 443, если 22 фильтруется по маршруту.
- Health-check переключает endpoint только после нескольких ошибок и проверяет Telegram через
  новый SOCKS до перезапуска ботов.
- Возврат на основной endpoint делать вручную либо с большим hysteresis, чтобы избежать flapping.

## Runbook для реакции

1. Проверить внешний статус VM/Web.
2. На VM проверить сокет `127.0.0.1:1080` и последние логи `tg-socks-tunnel`.
3. Проверить доступность внешнего VPN/VPS с VM и из другой сети.
4. Если VPS доступен из другой сети, проверить его firewall/fail2ban и блокировку публичного IP VM.
5. Восстановить tunnel или переключить резервный endpoint.
6. Убедиться реальным запросом, что Telegram доступен через SOCKS.
7. Проверить все bot-сервисы и остановившийся рост `NRestarts`.
8. Выполнить business catch-up: турниры, напоминания и импорты, запланированные на окно простоя.
9. Зафиксировать начало, восстановление, причину и предпринятые действия в этом документе или
   отдельном incident log.

## Следующее решение

Для первого внедрения выбрать один из вариантов:

- **Предпочтительно:** Better Stack/Healthchecks.io + email/mobile push, локальный systemd timer,
  внешний HTTP-check.
- Yandex Cloud Monitoring + email для инфраструктуры и Monium для приложения; функциональную
  проверку Telegram всё равно выполнять на VM.

После выбора сервиса нужно уточнить желаемые каналы эскалации и допустимо ли автоматическое
переключение на резервный VPN.
