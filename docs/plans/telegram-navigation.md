# Навигация Telegram-бота

Статус: **план принят, реализация не начата**
Дата обновления: **10 октября 2026 года**

Этот файл — живой план рефакторинга пользовательской навигации MetaGatherer. После
каждого merge нужно обновлять чекбоксы, статус этапа и ссылку на фактический PR. Не
считать этап выполненным по открытому или зелёному PR.

## 1. Проблема

Бот функционально большой, но сейчас пользователь должен:

- знать или найти slash-команду (`/tournaments`, `/settings`, `/cellar` и другие);
- понимать, какая из многочисленных inline-кнопок является следующим шагом;
- запоминать, где находится текущий турнир, статус, колода или рейтинг;
- угадывать, вернёт ли «Назад» к турниру, к списку или в начало;
- вручную выходить из состояний ввода имени, города, колоды или результата.

Текущий `/start` синхронизирует command menu, но показывает только текст с просьбой
ввести `/tournaments`. Это не полноценный главный экран. В коде уже есть много хороших
локальных навигационных кнопок, однако их правила и подписи не единообразны.

Цель — сделать интерфейс понятным человеку, который впервые открыл бота, не убирая
slash-команды для опытных пользователей и deep-link-сценариев.

## 2. Принятое решение

Используем гибридную навигацию:

1. Постоянная пользовательская клавиатура Telegram (`ReplyKeyboardMarkup`) — быстрый
   вход в основные разделы.
2. Inline-кнопки — навигация внутри выбранного раздела и действия над объектом.
3. На каждом вложенном экране — единая нижняя строка `← Назад` и `⌂ Главное меню`.
4. На главном экране — персональный контекст: текущий турнир и ближайшее полезное
   действие пользователя.
5. Slash-команды остаются рабочим запасным интерфейсом и не заменяются удалением
   обработчиков.

Постоянная клавиатура — это не отдельная бизнес-логика. Её кнопки маршрутизируют в те
   же Telegram-обёртки и handlers, которые уже используются командами.

## 3. Главное меню игрока

Базовая раскладка для обычного игрока:

```text
[🏟 Турниры]       [🎯 Мой статус]

[🃏 Колоды]        [📊 Рейтинги]

[🏅 Ачивки]        [⚙️ Настройки]
```

Подписи должны быть короткими, глагольными или предметными и понятными без знания
внутренней терминологии. Не использовать игровые метафоры вроде «Древние руины», если
по названию нельзя понять результат нажатия.

### Главный экран

`/start` без deep-link открывает сообщение с приветствием, кратким текущим статусом и
inline-действиями. Ответ зависит от состояния пользователя:

```text
Привет!

Сейчас у вас нет активной записи.

[📝 Записаться на турнир]
[📖 Как это работает]
```

Если пользователь уже записан:

```text
🎯 Ваш текущий турнир

Endstep Pauper · регистрация открыта
Колода: не указана

[Открыть мой турнир]
[🃏 Указать колоду]
```

Главный экран не должен дублировать все шесть разделов: они уже доступны в постоянной
клавиатуре. Его задача — показать контекст и предложить следующий шаг.

## 4. Информационная архитектура

### 🏟 Турниры

- активные и ближайшие турниры;
- текущий турнир пользователя первым;
- регистрация и отмена регистрации;
- карточка турнира;
- статус, паринги, раунд и ввод результата;
- архив отдельной кнопкой внизу списка.

### 🎯 Мой статус

- текущий турнир;
- зарегистрирован ли пользователь;
- заявленная колода и деклист;
- текущий раунд и соперник;
- быстрые действия, доступные именно в текущем состоянии.

Если активного турнира нет, раздел ведёт в список турниров с понятным объяснением, а
не показывает пустой экран.

### 🃏 Колоды

- каталог ячейки;
- ближайшие даты;
- доступные и занятые колоды;
- мои бронирования и отмена;
- мои деклисты, если функция доступна пользователю.

### 📊 Рейтинги

- Moscow Pauper Ranked;
- Endstep ru Pauper Ranked;
- социальный рейтинг;
- правила рейтинга и переход «Где я?».

### 🏅 Ачивки

Раздел открывает текущую доступную полку ачивок. Служебные preview и owner-only
операции не попадают в пользовательское меню.

### ⚙️ Настройки

- имя;
- Endstep-ник;
- город;
- настройки уведомлений;
- отображение эмодзи;
- статус в парингах.

## 5. Навигационный контракт

Каждый экран должен явно иметь родителя. В callback-клавиатурах используются только
известные callback-префиксы и необходимые числовые идентификаторы; произвольный текст
из callback не становится маршрутом.

| Уровень | Пример | Нижняя навигация |
|---|---|---|
| Главное меню | персональный home screen | постоянная клавиатура |
| Раздел | список турниров | `⌂ Главное меню` |
| Объект | карточка турнира | `← К турнирам` · `⌂ Меню` |
| Подраздел | статус / деклисты / рейтинг | `← Назад` · `⌂ Меню` |
| Ввод | имя, город, колода, результат | `❌ Отмена` · `⌂ Меню` |
| Подтверждение | выход, удаление, рассылка | `❌ Отмена` · действие |

Правила:

- `← Назад` возвращает на непосредственный логический родительский экран;
- `⌂ Главное меню` всегда доступно одним нажатием;
- переход по callback редактирует существующее сообщение, если это возможно;
- новое сообщение создаётся только для необходимого текстового ввода, фото, файла или
  отдельного результата;
- после `❌ Отмена` очищается соответствующее состояние `context.user_data`;
- deep-link открывает нужный экран напрямую, но получает те же кнопки возврата;
- устаревший callback не должен падать: пользователь получает короткое уведомление и
  кнопку возврата в главное меню;
- ошибки и пустые состояния предлагают следующий шаг, а не оставляют пользователя в
  тупике.

## 6. Роли и служебные функции

Главное меню обычного игрока не перегружается админскими действиями. Для организатора,
метаписца и администратора добавляется отдельный раздел:

```text
[🛠 Управление]
```

Внутри него могут находиться создание турнира, управление Swiss, AetherHub, выгрузки,
опросы и служебные debug-инструменты. Роли влияют только на видимость и удобство меню;
каждый handler всё равно обязан повторно проверять права.

Role-aware BotCommand menu сохраняется как fallback. Изменение постоянной клавиатуры не
должно открывать скрытые команды обычному пользователю.

## 7. План реализации по PR

### Этап 1 — главное меню и роутинг

- [ ] Добавить модель постоянной клавиатуры для обычного игрока.
- [ ] Добавить маршрутизацию текстовых кнопок в существующие пользовательские flow.
- [ ] Переделать `/start` в главный экран с контекстным статусом.
- [ ] Оставить существующие slash-команды и deep-link без регрессий.
- [ ] Зафиксировать кнопки и подписи в отдельном модуле UI-навигации.

Критерий: новый пользователь попадает к списку турниров максимум за одно нажатие после
открытия клавиатуры, а к регистрации — максимум за два.

### Этап 2 — единый возврат из основных пользовательских flow

- [ ] Ввести общий helper для строки `Назад / Главное меню`.
- [ ] Применить его к турнирам, карточке турнира, статусу и регистрации.
- [ ] Применить его к настройкам, рейтингу, ячейке и ачивкам.
- [ ] Добавить единый `Отмена` для всех состояний текстового ввода.
- [ ] Проверить, что старые сообщения не оставляют пользователя с неработающей кнопкой.

Критерий: из любого основного пользовательского экрана есть работающий путь в root за
одно нажатие.

### Этап 3 — контекст «Мой статус»

- [ ] Сделать отдельный read-first экран текущего турнира.
- [ ] Показывать разные действия для состояний «не записан», «записан без колоды»,
  «идёт раунд», «результат ожидает подтверждения», «турнир завершён».
- [ ] Добавить быстрые переходы к колоде, парингу, результату и карточке турнира.
- [ ] Не дублировать в меню действия, которые недоступны в текущем состоянии.

Критерий: пользователь понимает свой следующий шаг, открыв `🎯 Мой статус`, без чтения
справки и команд.

### Этап 4 — отдельное меню организатора

- [ ] Добавить условный раздел `🛠 Управление` только для подходящих ролей.
- [ ] Сгруппировать служебные действия по турниру, клубу и диагностике.
- [ ] Убрать служебные кнопки из основной карточки игрока, оставив необходимые действия
  в контекстном меню.
- [ ] Проверить owner-only и debug-only ограничения.

### Этап 5 — полировка и измерение

- [ ] Проверить тексты на маленьком экране и в русской локали Telegram.
- [ ] Убедиться, что подписи кнопок помещаются в две колонки и не обрезаются.
- [ ] Добавить события аналитики: открытие home, раздела, отмена и возврат.
- [ ] Сравнить долю успешных переходов и отмен до/после без записи персональных данных.
- [ ] Обновить этот план после каждого merge.

## 8. Тестирование

### Unit и handler tests

- exact routing каждой кнопки постоянного меню;
- role-aware меню для игрока, организатора и администратора;
- parent callback для каждого основного экрана;
- очистка pending input state после отмены;
- недоступный или устаревший callback;
- пустые состояния: нет турниров, нет текущего турнира, нет колоды, нет рейтинга.

### In-process Telegram E2E

Расширить существующий безопасный harness из
[`docs/telegram_e2e.md`](../telegram_e2e.md):

- `/start` → главное меню → `🏟 Турниры` → карточка турнира;
- карточка → `← Назад` → список;
- список → `⌂ Главное меню` → home;
- `🎯 Мой статус` при разных состояниях пользователя;
- настройки → текстовый ввод → `Отмена`;
- проверка, что все сообщения уходят только разрешённому synthetic chat ID;
- только fake token, in-memory SQLite и network-deny guard.

### Acceptance smoke

На debug-боте вручную проверить три профиля:

1. новый пользователь без активной записи;
2. записанный игрок без колоды;
3. организатор/администратор.

В production smoke этот план не включает никаких новых массовых рассылок или операций с
реальными турнирами.

## 9. Обновление статуса после merge

После каждого PR:

1. проверить, что PR действительно merged в `main`;
2. обновить чекбоксы и статус соответствующего этапа;
3. добавить ссылку на PR и краткий фактический результат;
4. отметить оставшиеся ограничения или технический долг;
5. не помечать весь этап завершённым, если реализована только часть flow.

## 10. Что не входит в этот план

- новая бизнес-логика турниров;
- изменение правил регистрации, Swiss или голосований;
- массовые уведомления игрокам;
- полноценный redesign веб-интерфейса;
- изменение авторизации и связки Telegram/email для web;
- автоматический реальный Telegram smoke в каждом PR.
