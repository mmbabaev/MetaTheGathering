# План безопасного теста оплаты в debug

## Цель

Проверить полный путь тестового платежа через ЮKassa: кнопка в карточке турнира → создание
платежа → тестовая форма оплаты → webhook → статус «оплачено» в базе и Telegram. Тест проводится
только в debug-окружении и только через тестовый магазин ЮKassa: без реальных карт и списаний.

Официальные инструкции:

- [тестирование платежей](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing);
- [входящие уведомления](https://yookassa.ru/developers/using-api/webhooks).

## Текущее состояние

- Feature flag `payment` в debug включён, и зарегистрированный игрок видит кнопку оплаты.
- Сумма по умолчанию — `525.00 RUB`.
- В debug не заданы `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`, поэтому кнопка сообщает, что
  оплата не настроена.
- Обработчик `POST /webhook/yookassa` реализован в `web/api/app.py`, но debug systemd запускает
  `web.app:app`, где этот маршрут не подключён. Сейчас webhook получает `404`.
- Debug web доступен на HTTP-порту `8081`, а ЮKassa принимает webhook URL только по HTTPS на
  поддерживаемом порту (`443` или `8443`).
- `return_url` сейчас всегда ведёт в production-бота.
- Текущий webhook доверяет входному JSON и не перепроверяет платёж через API ЮKassa. Перед
  публикацией внешнего URL это необходимо исправить.
- Успешная оплата только меняет статус записи `Payment` и карточку игрока. Игрок должен быть
  зарегистрирован в турнире заранее; оплата сама по себе не регистрирует участника.

## Этап 1. Подготовить безопасное debug-окружение

1. Создать тестовый магазин в кабинете ЮKassa.
2. Добавить его тестовые `ShopID` и secret key в GitHub secret `ENV_FILE_DEBUG`. Значения не
   записывать в git, логи, документацию или сообщения.
3. Добавить отдельную настройку `PAYMENT_RETURN_URL` и указать debug-бота для debug-окружения.
4. Оставить `PAYMENT_AMOUNT` отдельной настройкой. Для первого прогона использовать тестовую
   сумму; тестовый магазин всё равно не списывает реальные деньги.
5. Убедиться, что flag `payment` включён только в debug-клубе/сценарии, выбранном для проверки.

Критерий готовности: кнопка создаёт платёж тестового магазина, ссылка открывает тестовую форму,
а production credentials и production-бот нигде не используются.

## Этап 2. Подключить и защитить webhook

1. Подключить роутер оплаты к фактически запускаемому `web.app:app`, не создавая второй независимый
   FastAPI application.
2. Выдать debug отдельный публичный HTTPS URL на порту `443` или `8443` и направить его на debug-web.
3. Зарегистрировать в тестовом магазине URL вида `https://<debug-host>/webhook/yookassa` только для
   события `payment.succeeded`.
4. Не принимать статус из входного JSON на доверии. Получить платёж по его ID через API ЮKassa и
   проверить:
   - `status == succeeded`;
   - `paid == true`;
   - сумму и валюту;
   - test/live режим;
   - соответствие `metadata.tg_id` и `metadata.tournament_id` локальной записи;
   - что локальный платёж ещё не был обработан.
5. Обрабатывать повторные webhook идемпотентно: повтор не должен повторно менять состояние или
   отправлять второе уведомление.
6. Не логировать ключи, полные payload с персональными данными и ссылки подтверждения.

Критерий готовности: поддельный, неизвестный или изменённый webhook не подтверждает оплату;
валидный повтор возвращает успешный HTTP-ответ без повторного Telegram-сообщения.

## Этап 3. Автоматические тесты

До ручного прогона добавить тесты без сетевых запросов:

- feature flag выключен — кнопки нет;
- flag включён, но ключей нет — понятный alert без обращения к ЮKassa;
- успешное создание платежа сохраняет `PENDING`, сумму, турнир и пользователя;
- ошибка/timeout ЮKassa не создаёт частично заполненную запись;
- валидный `payment.succeeded` переводит только нужный платёж в `SUCCEEDED`;
- неверная сумма, валюта, metadata, live/test режим или статус отклоняются;
- неизвестный payment ID ничего не меняет;
- повторная доставка события идемпотентна;
- fallback Telegram-сообщение отправляется только плательщику;
- карточка этого игрока показывает «Оплачено», карточки остальных не меняются.

Тесты не должны использовать строк, похожих на реальные секреты. Для заглушек использовать явно
фиктивные значения, например `dummy-not-a-real-key`.

## Этап 4. Ручной end-to-end прогон

1. Создать отдельный debug-турнир и записаться в него своим debug-аккаунтом.
2. Открыть карточку турнира и проверить наличие кнопки «Оплатить взнос».
3. Нажать кнопку один раз и проверить, что бот показывает сумму и ссылку тестового магазина.
4. Провести успешную оплату тестовой картой из документации ЮKassa.
5. Проверить:
   - webhook получил HTTP `200`;
   - в БД ровно одна запись стала `SUCCEEDED`;
   - исходное сообщение заменилось на подтверждение или пришёл один адресный fallback;
   - карточка турнира показывает «Оплачено»;
   - другим игрокам ничего не отправлено.
6. Повторно доставить тот же webhook и убедиться, что второго уведомления нет.
7. Отдельно пройти сценарии отмены/возврата на форму, неуспешной карты и истечения ссылки. Во всех
   случаях локальный статус не должен стать `SUCCEEDED`.
8. Отправить изменённый тестовый payload с неверной суммой или metadata и убедиться, что он
   отклонён без изменения БД.

## Этап 5. Завершение проверки

1. Выключить flag `payment` в debug, если следующий тест не запланирован.
2. Удалить временный debug-турнир и тестовые платежи штатным способом, если они мешают дальнейшим
   проверкам.
3. Сохранить только безопасные результаты: время теста, локальный ID платежа, HTTP-статусы и итог.
   Secret key и confirmation URL в отчёт не включать.
4. Перед production-пилотом отдельно согласовать семантику оплаты: является ли она только отметкой
   взноса или должна гарантировать/создавать регистрацию, что делать с возвратами, повторной оплатой
   и закрытым турниром.

## Критерии успешного теста

- Ни одного реального списания и ни одного обращения к production-магазину.
- Платёж создаётся только для инициатора и выбранного турнира.
- Подтверждение возможно только после серверной проверки данных через ЮKassa.
- Повторные события безопасны и не создают повторных уведомлений.
- Telegram-сообщение получает только заплативший пользователь.
- Статус оплаты одинаково отображается после перезапуска bot/web процессов.
- В логах и git нет секретов и платёжных ссылок.
